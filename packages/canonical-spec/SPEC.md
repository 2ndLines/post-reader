## 1. 输入

- 输入是 Unicode 标量值序列。孤立代理在进入第 1 步之前替换为 U+FFFD（TS 实现调用 `String.prototype.toWellFormed()`；Swift 的 `String` 不会出现孤立代理）。
- 下文中的「码位」都指 Unicode 标量值。各步按顺序执行，每一步的输入是上一步的输出。

## 2. 清洗（`clean`）

### 第 1 步 · 解码 HTML 实体（只解码一遍）

从左到右扫描，下列形式替换为对应的码位：

| 形式 | 结果 |
| --- | --- |
| `&#` + 1–7 位十进制数字 + `;` | 该码位 |
| `&#x` 或 `&#X` + 1–6 位十六进制数字 + `;` | 该码位 |
| `&amp;` `&lt;` `&gt;` `&quot;` `&apos;` `&nbsp;` | `&` `<` `>` `"` `'` U+00A0 |

- 数字实体的码点为 0、位于 U+D800–U+DFFF，或大于 U+10FFFF 时，结果为 U+FFFD。
- 其他所有形式（不认识的命名实体、缺少 `;`、位数超出）原样保留。
- 解码只做一遍：`&amp;lt;` 的结果是 `&lt;`，不会再解码成 `<`。
- 命名实体区分大小写：`&AMP;` 原样保留。
- **清洗不是幂等的**：清洗结果中可能仍含实体形式的文本（例如原文 `&amp;lt;` 清洗为 `&lt;`），再清洗一次会变成 `<`。所以清洗只能对原文做一次；已经清洗过的文本不得再次清洗。服务端重算摘要时，应对客户端上报的 `cleanText` 直接计算摘要，或对原文重新清洗，不得对 `cleanText` 再清洗（Q7）。

> 默认解读 Q5：不实现完整的 HTML5 命名实体表。

### 第 2 步 · NFC

按 Unicode 规范化形式 C（NFC）规范化。

### 第 3 步 · 统一换行并删除控制字符

1. 先把下列换行形式统一为 U+000A：U+000D U+000A（CRLF）、单独的 U+000D、U+0085（NEL）、U+2028（LS）、U+2029（PS）。
2. 再删除下列码位：

| 码位 | 说明 |
| --- | --- |
| U+0000–U+0009、U+000B–U+001F | C0 控制字符，保留 U+000A。U+0009（制表符）也删除，见 Q2 |
| U+007F–U+009F | DEL 与 C1 控制字符 |
| U+FEFF | BOM / ZWNBSP |
| U+200B、U+2060 | 零宽空格、词连接符 |
| U+202A–U+202E | 双向嵌入、覆盖控制字符（LRE、RLE、PDF、LRO、RLO） |
| U+2066–U+2069 | 双向隔离控制字符（LRI、RLI、FSI、PDI） |

> 默认解读 Q1：00 §3.2 原文先删除控制字符、后统一换行。这样单独出现的 CR 会先被删掉，两侧的行被连成一行，所以统一换行提前到删除之前。
>
> 默认解读 Q2：制表符按原文删除。待负责人确认是否改为替换为空格。

U+200E、U+200F（LRM、RLM）与 U+061C（ALM）不在 00 §3.2 的删除列表中，保留。

### 第 4 步 · ZWNJ（U+200C）与 ZWJ（U+200D）

第 3 步输出中的每个 U+200C、U+200D，满足下列条件之一就保留，否则删除。判定时看的是第 3 步输出中的相邻码位：先判定完全部 ZWNJ/ZWJ，再统一删除，所以前一个码位的删除不影响后一个的判定。

- **emoji 上下文（只适用于 ZWJ U+200D）**：
  - 前一个码位：从 ZWJ 向前跳过所有 U+FE0F、U+FE0E 后遇到的第一个码位，它具有 Unicode `Emoji` 属性，且不小于 U+0080；
  - 后一个码位：紧接在 ZWJ 之后的码位，同样具有 `Emoji` 属性，且不小于 U+0080。
  - 两者都满足时保留。排除小于 U+0080 的码位，是因为 `#`、`*`、`0`–`9` 也具有 `Emoji` 属性。
- **连写文字上下文（ZWNJ 与 ZWJ 都适用）**：紧邻的前一个码位与后一个码位都落在下表任一区段内：

| 区段 | 文字 |
| --- | --- |
| U+0600–U+06FF、U+0750–U+077F、U+0870–U+089F、U+08A0–U+08FF | 阿拉伯文及扩展 |
| U+FB50–U+FDFF、U+FE70–U+FEFE | 阿拉伯文表现形式 |
| U+0700–U+074F、U+0860–U+086F | 叙利亚文及补充 |
| U+07C0–U+07FF | N'Ko |
| U+0900–U+0D7F | 天城文至马拉雅拉姆文 |
| U+0D80–U+0DFF | 僧伽罗文 |
| U+1800–U+18AF | 蒙古文 |

> 默认解读 Q3、Q4：00 §3.2 没有定义「emoji 序列」与「连写文字上下文」。这里用明确的码位区段，不用 Unicode Script 属性，因为 Swift 没有提供 Script 属性的 API。
>
> `Emoji` 属性：TS 用 `\p{Emoji}`，Swift 用 `Unicode.Scalar.Properties.isEmoji`。新 emoji 在两侧平台的 Unicode 版本中可能不同，向量只使用 Unicode 15.1 及更早版本中的 emoji。

### 第 5 步 · 空行与首尾空白

本步的「空白码位」是 Unicode `White_Space` 属性中经过第 3 步后仍可能出现的码位：

U+0020、U+00A0、U+1680、U+2000–U+200A、U+202F、U+205F、U+3000

1. 按 U+000A 切分为行。整行只由空白码位组成的行，变为空行。
2. 用 U+000A 重新连接。连续 3 个及以上的 U+000A 折叠为 2 个，即段落之间最多保留一个空行。
3. 去除首尾的空白码位与 U+000A。

行内空白与行尾空白不做处理（Q6）。

### 第 6 步 · 不做 SSML 转义

`<`、`>`、`&` 等字符在清洗结果中原样保留。SSML 转义在 TTS 边界进行（D3，P3）。

## 3. 摘要（`hash`）

```text
H = hex( SHA256( lp(unitId) ‖ lp(authorId) ‖ lp(cleanText) ) )
lp(x) = uint32_be( len(utf8(x)) ) ‖ utf8(x)
```

- `cleanText` 是第 2 节对原文清洗后的结果。`unitId` 与 `authorId` 不做清洗，按原值进入摘要。
- `hex` 输出 64 个小写十六进制字符。
- 例：`lp("ab")` 的字节为 `00 00 00 02 61 62`，`lp("")` 的字节为 `00 00 00 00`。

## 4. 向量

`vectors/*.json` 中每个文件是一个数组，每项包含：

| 字段 | 说明 |
| --- | --- |
| `name` | 全局唯一的短名 |
| `raw` | 原文 |
| `unitId`、`authorId` | 参与摘要的标识 |
| `expectedClean` | **人工写出**的清洗结果，不由任何实现生成 |
| `expectedHash` | 由 `scripts/expected_hash.py`（只用 Python 标准库，与 TS、Swift 实现都无关）根据 `expectedClean` 计算 |
| `note` | 可选，说明这条向量覆盖的规则 |

重新计算或校验 `expectedHash`：

```bash
python3 packages/canonical-spec/scripts/expected_hash.py          # 只校验，不一致时退出码为 1
python3 packages/canonical-spec/scripts/expected_hash.py --write  # 回写
```

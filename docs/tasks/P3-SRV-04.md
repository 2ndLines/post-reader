# P3-SRV-04 quota：两层计量、原子核销、退还、软着陆

## 验收标准（助手起草，2026-11-27；负责人确认前视为草案）
1. 发放：同一用户同一账期只发一次，写 `grant` 流水；没有账期时预检不通过 —— 集成测试
2. `settleCall`：
   - 底层记录原始用量与成本，不含用户 ID；用户侧按本期 `rate_version` 的系数折算、向上取整，余额同步减少
   - 同一 `(jobId, stage, seq)` 只核销一次
   - 一次调用含多项计价单位时，分别折算后相加
   —— 集成测试
3. 不计入额度（`billable = false`）或没有用户：只写底层 —— 集成测试
4. 容错不加价：备用渠道折算更贵时，按主渠道的等价用量计 —— 集成测试
5. 软着陆：余额 > 0 时发起，结算后可以为负，之后预检不通过 —— 集成测试
6. 并发：同一账户 20 次并发结算后，余额 = 发放 − Σ扣减 —— 集成测试
7. 失败即关闭：找不到系数、单价或生效中的账期时拒绝结算，什么都不写 —— 集成测试
8. 退还：
   - 完整性失败只退该单元的翻译与语音合成，文本生成不退
   - 任务失败时退还全部扣减
   - 重复退还无效；底层用量不变；对账口径「余额 = 发放 − Σ流水」成立
   —— 集成测试
9. `pnpm verify`、`pnpm test:int`、`knip`、迁移不可变检查、`ci` 与 `integration` 工作流全绿

## 计划（助手填写）
- **表**：按《完整技术架构》§11.2 建四张表，暂不分区（R1）。幂等键用普通唯一约束，直接保证只核销一次。
- **退还的定位**：通过 `quota_ledger.usage_id → vendor_usage(job_id, stage, seq)` 找到要退的扣减，所以流水表不重复存 `job_id`、`seq`。
- **退还的规则**：
  - 退回扣减时所在的账期。
  - 幂等键按 02 §18.2 写为 `refund:{jobId}:{stage}:{seq}`。
  - 先锁余额行，再写流水，加锁顺序与 `settleCall` 一致。
- **失败即关闭**：系数、单价或账期缺失时抛错，整个事务回滚，不按 0 记账。
- **新依赖**：无。

## 风险与问题（助手填写）
- **Q1 容错不加价的等价用量**：02 §9.2 的 `primaryEquivalentMc` 需要「同一请求按主渠道计价单位的估算」。备用渠道的计价单位可能不同（例如按字符计与按秒计），服务端无法自行换算，所以改由调用方传入 `primaryEquivalentItems`；有 `failoverFrom` 时必填。
- **Q2 没有生效中的账期时结算**：默认拒绝，事务回滚，底层用量也不写。这意味着这种情况下成本记录会缺失，但它只会出现在发放逻辑有缺陷时，应该告警而不是静默记账。负责人如果希望先记底层、再告警，改为两段写入。
- **Q3 `vendor_usage` 的归属**：02 §5.6 写的是「表 `vendor_usage`（与 `tts` 共用）」。目前唯一的写入方是 `settleCall`，所以先放在 quota 模块。
- **R1 分区**：`vendor_usage` 与 `quota_ledger` 设计为按月分区（13 个月保留）。drizzle-kit 不生成分区表，分区与保留期任务另开任务卡。分区之后，唯一约束必须包含分区键，幂等改为「Redis `SET NX` + 当月分区内唯一」两层（《完整技术架构》§11.2）。
- **R2 舍入**：每个计价单位分别向上取整后相加，与 02 §9.2 的参考实现一致。同一调用的多个单位因此最多多计「单位数 − 1」毫点。

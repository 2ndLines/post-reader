# 0017 本地验证 V1（Node 26 工具链）与 V4（SeaweedFS S3 行为）结论

- 状态：提议（实测完成，待负责人批准）
- 日期：2026-11-26

## 背景

05 §1.2 规定，P0 要实测两项「默认」选择，结论写进 ADR：

- **V1**：在 Node 26 下，BullMQ、Testcontainers、drizzle-kit、promptfoo、Pulumi 能否正常使用。不通过则回退到 Node 24。
- **V4**：本地 S3 替身 SeaweedFS 的预签名 URL、分段上传、`DeleteObjects` 三类操作，行为是否与 AWS S3、阿里云 OSS 一致。不通过则换另一种替身。

验证脚本在 `tools/verify/`（任务卡 P0-REPO-05）。它是一个独立项目，有自己的锁文件，供应链设置与主工作区相同，但它的依赖不进入主工作区。原因是这些库属于 P2、P3 阶段，提前装进主工作区会影响 knip、许可证门禁和锁文件。

**验证环境**：

- 时间：2026-11-26
- 系统：macOS，arm64
- 运行时与工具：Node 26.13.1（mise），Docker 29.9.3
- 本地容器：由 `docker-compose.yml` 启动，镜像按多架构 digest 固定。版本为 postgres 18.7、valkey 8.1.12、seaweedfs 4.55、mailpit v1.34.0。

**被测库的版本**（pnpm `minimumReleaseAge` 3 天规则选出，全部固定为精确版本）：

| 库 | 版本 |
| --- | --- |

| ioredis | 6.1.0 |

| drizzle-orm | 0.45.4 |

## 决策

**V1 通过，维持 Node 26 基线。** 实测输出见任务卡 P0-REPO-05 的交接记录：

| 项 | 结果 |
| --- | --- |
| BullMQ | 向 Valkey 入队并消费 1 个任务，返回值正确 |
| Testcontainers | 用 `docker-compose.yml` 中同一 digest 的 postgres 与 valkey 镜像启动容器，执行查询与 PING 均成功 |
| drizzle-kit | 在临时数据库上，`generate --custom` 生成一个空迁移，`migrate` 执行后迁移记录为 1 条 |
| promptfoo | 用 echo provider 运行一条 `equals` 断言，通过；关闭遥测，不分享，不写用户目录 |
| Pulumi CLI | 用本地 file 后端（不 `login`）对空的 YAML stack 执行 `preview`，成功 |

**V4 通过，维持 SeaweedFS。** 共 15 项检查，与 AWS S3 文档描述的行为全部一致：

| 类别 | 检查项 | SeaweedFS 实测 | AWS S3（文档） | 阿里云 OSS（文档） |
| --- | --- | --- | --- | --- |
| 预签名 | PUT 上传，再 GET 读取，比对内容与 Content-Type | 一致 | 同 | 同（S3 兼容接口，P10 验证签名版本，05 §4.2） |
| 预签名 | 篡改签名 | 403 | 403 SignatureDoesNotMatch | 403 |
| 预签名 | 过期后访问 | 403 | 403 | 403 |
| 预签名 | 签发有效期超过 7 天的链接 | SDK 在签发时拒绝 | SigV4 上限 7 天 | 未查到 V4 的上限，P10 实测 |
| 分段上传 | 5 MiB + 1 KiB 两段合并；合并后 ETag 形如 `"<md5>-2"` | 一致 | 同 | 同 |
| 分段上传 | 非最后一段小于 5 MiB | `EntityTooSmall` | `EntityTooSmall`（下限 5 MiB） | **下限 100 KB** |
| 分段上传 | 取消上传后再列出分段 | `NoSuchUpload` | 同 | 同 |
| DeleteObjects | 一次删除 3 个已存在的键和 1 个不存在的键 | 4 个键都列入 Deleted，Errors 为 0 | 同（不存在的键也报告删除成功） | 同 |
| DeleteObjects | Quiet 模式 | Deleted 为空 | 同 | 同 |
| DeleteObjects | 单次 1001 个键 | `MalformedXML` | 单次上限 1000 | 单次上限 1000 |
| SDK 默认行为 | `PutObject` 默认附带 CRC32 校验和 | 接受 | 接受 | P10 实测 |

**由此确定的实现约束**（P2 写入 05 §4.2 与 `platform/storage`、`platform/queue`）：

1. **签发预签名 PUT 必须用 `requestChecksumCalculation: 'WHEN_REQUIRED'`。** SDK 默认值为 `WHEN_SUPPORTED`，这时会把签发时空内容的 CRC32 写进 URL，上传真实内容时校验和对不上，返回 `BadDigest`。这是 SDK 的行为，AWS S3 同样会拒绝；实测中这一项归入「SDK 默认行为」。
2. **分段上传统一按 5 MiB 下限切段。** 这个值同时满足 S3 与 OSS（OSS 下限 100 KB），本地替身也能复现「段过小」的错误。
3. **单次 `DeleteObjects` 最多 1000 个键**，超过时由调用方分批。
4. **BullMQ 6 起 ioredis 是可选 peer。** 在原生 ESM 下必须传入已构造好的 `ioredis` 实例，不能只传连接参数；Queue 与 Worker 各用一个专用连接（`maxRetriesPerRequest: null`）。`ioredis` 已在 05 §4.2 登记为「已定」。
5. **promptfoo 0.126.0 的依赖树与 `strictPeerDependencies: true` 有两处冲突**：`nunjucks>chokidar` 期望 3，实际为 6；`mongodb>gcp-metadata` 期望 7，实际为 9。验证项目只对这两对用 `peerDependencyRules.allowedVersions` 放行，严格模式不关。P3 在 `apps/testbench` 引入 promptfoo 时，需要把同样的两条规则写进根目录 `pnpm-workspace.yaml`，并在当时的 PR 中重新核对。另外，promptfoo 的任何调用（包括 `--help`）都会创建 `~/.promptfoo`，并写入一个 `id`。实测中设置 `PROMPTFOO_CONFIG_DIR` 指向临时目录后，用户目录保持干净。P3 必须为所有调用固定设置 `PROMPTFOO_CONFIG_DIR`（台架工作目录或临时目录）。Pulumi 同理，需要设置 `PULUMI_HOME`，并且不执行 `login`。
6. **许可证（P3 引入 promptfoo 前需负责人决定）**：用 `tools/ci-checks` 的同一套许可证策略检查验证项目，594 个包中有 13 个不在当前清单内（05 §2.2）。这些都来自 promptfoo 与 testcontainers 的依赖树，具体是：
   - BlueOak-1.0.0：9 个，包括 glob、minimatch、lru-cache、jackspeak 等
   - PSF-2.0：1 个，argparse
   - LGPL-3.0-or-later：1 个，`@img/sharp-libvips-*`
   - `SEE LICENSE IN LICENSE`：1 个，`@modelcontextprotocol/server-filesystem`
   - Unknown：1 个，sylvester

   BlueOak 与 PSF 都是宽松许可证，但把它们加进允许清单等于修改门禁，要由负责人决定。LGPL 的 libvips 只在 testbench 开发与 CI 中使用，不进入产物，按 05 §2.2「以子进程方式调用的二进制」处理，还是写进 `exceptions`，也待负责人决定。另外两项要在引入前查清实际许可证。本 PR 不修改许可证策略。
7. **安装脚本**：本次涉及 cpu-features、ssh2、msgpackr-extract 三个可选原生加速，以及 esbuild、protobufjs 的安装后自检，`allowBuilds` 中全部设为 `false`，实测各库功能正常。

## 备选方案与不选的理由

- **回退 Node 24**：V1 全部通过，没有回退的理由。
- **换另一种 S3 替身**：V4 全部一致，不需要更换。MinIO 已不可用（05 §3.2）。
- **把验证依赖装进主工作区**：会提前引入 P2、P3 才用的约 650 个包，影响 knip、许可证门禁和主锁文件；这些库正式引入时仍要各自按 05 §2.7 走一遍。

## 后果（正面、负面、需要跟进的事项）

- **正面**：Node 26 与本地容器方案都有了实测依据；上面 1–6 条约束在写代码之前就已经知道。
- **负面**：
  - `tools/verify` 有一份独立的锁文件需要维护。验证完成后，它只作为回归脚本保留。
  - CI 不跑这些脚本，因为它们需要 Docker 和本地容器。
- **需要跟进**：
  - P2 引入 BullMQ、S3 SDK 时，把约束 1–4 写进代码和测试。
  - P3 引入 promptfoo 时，处理约束 5，并由负责人对约束 6 中的许可证作出决定。
  - P10 用 OSS 实测预签名有效期上限和 CRC32 校验和。
- **未查明的现象**：首次运行时没有安装 ioredis，Node 进程以 `Abort trap: 6` 退出（退出码 134），而不是正常抛出异常。装上 ioredis 后无法再复现原条件，原因未查明。P2 在 `platform/queue` 中加一条「缺少依赖时能正常报错」的测试。

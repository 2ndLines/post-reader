# 0018 配置包签名算法按区确定：海外区 Ed25519，国内区 ECDSA P-256

- 状态：提议（依据官方文档得出；只读 API 复核待负责人）
- 日期：2026-11-26

## 背景

配置包的发布流程见 00 §5：打包、签名、上传两区、客户端与服务端验签。设计中写的签名算法是 Ed25519（00 §5、02 §2 `platform/crypto`、02 §3 环境变量 `CONFIG_BUNDLE_PUBKEYS`）。

两区独立部署（ADR 0001），每区用本区的 KMS 非对称密钥签名，私钥不出 KMS。05 §1.2 的 V5 要求在 P0 查明：两区的 KMS 是否都支持 Ed25519 签名。

- **不支持时的预定回退**：该区改用 ECDSA P-256，客户端同时接受两种算法。
- **任务卡 P0-REPO-05 要求的证据**：官方文档，加上只读 API 查询（列出可用的密钥规格）。

## 证据（2026-11-26 查阅）

- **AWS KMS（海外区）：支持。**
  - [Key spec reference](https://docs.aws.amazon.com/kms/latest/developerguide/symm-asymm-choose-key-spec.html) 列出 `ECC_NIST_EDWARDS25519`（ed25519），只用于签名与验签，签名算法有两种：
    - `ED25519_SHA_512`：必须用 `MessageType: RAW`。
    - `ED25519_PH_SHA_512`：必须用 `MessageType: DIGEST`。
    - 两种消息类型不能混用。
  - 公钥可以通过 `GetPublicKey` 导出到 KMS 之外使用。
  - [发布公告](https://aws.amazon.com/about-aws/whats-new/2025/11/aws-kms-edwards-curve-digital-signature-algorithm/)（2025 年 11 月）称所有区域可用。
- **阿里云 KMS（国内区）：不支持。**
  - [密钥管理类型和密钥规格](https://help.aliyun.com/zh/kms/user-guide/key-types-and-specifications)（与 document_detail/480161 为同一页面）中，非对称密钥只有软件密钥与硬件密钥两种管理类型，规格为：
    - RSA_2048、RSA_3072、RSA_4096
    - EC_P256、EC_P256K（签名算法 `ECDSA_SHA_256`）
    - EC_SM2（仅硬件密钥）
    - ML_DSA_44、ML_DSA_65、ML_DSA_87
  - 全页没有 Ed25519，也没有 EdDSA。
  - [CreateKey 接口文档](https://help.aliyun.com/zh/kms/key-management-service/developer-reference/api-kms-2016-01-20-createkey)的 KeySpec 参数直接引用上述页面，同样没有 Ed25519。
  - 某个搜索结果的摘要声称「软件密钥支持 Ed25519（EdDSA）」，与上述两份原始页面不符，不予采信。
- **只读 API 复核**：需要两区云账号的只读权限，助手不使用本机上的任何云凭据（playbook §1.3），这一步待负责人执行。可用的查询方式：
  - 海外区：`aws kms list-keys`，配合对已有密钥调用 `describe-key`，或在控制台的「创建密钥」页面查看可选规格。
  - 国内区：`aliyun kms DescribeKey`，或在控制台的「创建密钥」页面查看可选规格。

## 决策

执行 05 §1.2 预定的回退：

1. **签名算法**：海外区用 Ed25519（AWS KMS `ECC_NIST_EDWARDS25519` 与 `ED25519_SHA_512`，`MessageType: RAW`）；国内区用 ECDSA P-256（阿里云 KMS `EC_P256` 与 `ECDSA_SHA_256`）。
2. **签名信封带算法标识**：`alg` 的取值为 `Ed25519` 或 `ES256`，`kid` 指向公钥。验签方根据 `kid` 找到公钥，并要求该公钥登记的 `alg` 与信封中的一致。这样可以防止算法混淆：不允许用一种算法的公钥去验另一种算法的签名。
3. **ECDSA 签名统一用 IEEE P1363 原始格式**（`r‖s`，64 字节）。KMS 返回的是 DER 编码，由签名端转换。这样 Web Crypto（Node 26、Workers）与 CryptoKit（`P256.Signing.ECDSASignature(rawRepresentation:)`）都能直接验签。
4. **验签方同时支持两种算法**：iOS `ConfigService`、主体后端 `platform/config-bundle`、边缘层 `GET /config/bundle`。
   - `CONFIG_BUNDLE_PUBKEYS` 改为带 `alg` 与 `kid` 的公钥列表，仍支持多把并存，用于轮换。
   - 客户端内置两区的公钥。区域由 ADR 0001 判定，每个区只接受本区登记的 `kid`。
5. **签名 URL 不在本 ADR 范围内**：`packages/signed-url` 只用于海外区（主体后端签发、边缘层校验，D18）。它的密钥不是 KMS 非对称签名密钥，所以不受 V5 影响，计划不变。国内区的切片分发方式见 02 §22.1「国内区」一行，与 V5 无关。

## 备选方案与不选的理由

- **两区都改用 ECDSA P-256**：算法会统一，但海外区放弃了已有的 Ed25519，而 D18 的签名 URL 仍用 Ed25519，结果系统里照样有两种算法，并没有因此变简单；而且客户端反正要内置两区的公钥。
- **国内区用软件签名（私钥放在凭据管理服务，进程内签名）以保留 Ed25519**：私钥会离开 KMS，削弱密钥保护，属于红线（不弱化安全控制）。
- **国内区用 EC_SM2**：只有硬件密钥支持；iOS CryptoKit 与 Web Crypto 都不原生支持 SM2，需要引入第三方密码库。

## 后果（正面、负面、需要跟进的事项）

- **正面**：两区的私钥都留在 KMS 内；预定的回退落地，没有新增依赖。
- **负面**：验签代码要支持两种算法，黄金向量也要覆盖两种算法。
- **需要跟进**：
  - P1-CTR-04 / `packages/config-schema`：在配置包签名信封的 schema 中加入 `alg`、`kid`。
  - P2 `platform/crypto`：实现 Ed25519 与 ES256（P1363）两种验签，补充算法混淆测试。
  - P4 / P8 iOS `ConfigService`：两种算法都要验签，测试复用同一组黄金向量。
  - 负责人用只读 API 复核两区结论。如果阿里云届时已支持 Ed25519，国内区可以改回 Ed25519，并在本 ADR 记录。

# Post&Comments Reader 技术选型分析

Nov 25, 2026 · @Haijun Shi · 依据：主 PRD v2.7 草案与三份子 PRD v1.3（初版依据 PRD v2.6.5）

## 结论摘要

推荐“iOS 纯原生 + 其余全部 TypeScript”：后端、管理后台、测试台架共用一个 monorepo 和一套类型定义，同一份代码部署到阿里云（国内）和 AWS（海外）两套互不相通的环境。

| 子系统 | 推荐技术栈 | 一句话理由 |
| --- | --- | --- |
| iOS 客户端 | Swift 6 + SwiftUI，最低 iOS 18；GRDB + SQLCipher；AVAudioEngine；WKWebView 单实例；StoreKit 2 | 15 MB / 80 MB 内存上限与音频、凭证要求只有原生能满足 |
| 后端服务 | Node.js 26 + Fastify + zod；PostgreSQL 18 + Redis；BullMQ；国内 OSS / 海外 R2；阿里云 SAE / AWS Fargate（美国）；海外边缘层 Cloudflare Workers + Hono；Pulumi | 以 IO 等待为主的编排负载，一门语言覆盖三个 Web 子系统 |
| AI 与语音 | 国内豆包 / 千问 + 豆包语音 2.0；海外 Claude（Bedrock 或 ZDR）+ ElevenLabs 或备选 TTS；自建薄模型网关 | 两区供应商必然不同，业务代码只对网关编程 |
| 管理后台 | React + Vite + Refine + Ant Design 5；独立 `admin-api`；Passkey + 零信任网关；两区各一套 | 表格表单密集的内部工具，数据不出区 |
| 后端 Web 测试台架 | React + Vite；直接驱动流水线模块；promptfoo + Vitest；ffmpeg EBU R128；GitHub Actions | 同时是调试工具和 PRD 第 12 节门禁的执行器 |

**三条最关键的判断**

1. 端云一致性是这个产品的核心技术风险：清洗与摘要规则要写成规格和黄金向量，Swift 与 TypeScript 两侧各实现一遍并同时跑测试；云端也要对实际送进 TTS 的文本重算摘要，而不是原样回传。
2. PRD 有几处按原文无法实现：国内不能用 R2，WebKit 的 Cookie 默认不在 Keychain，分钟级缓存存活期不能靠生命周期规则，Share Extension 不能主动打开主 App，详见“PRD 需修正”一节。
3. 工期风险主要来自外部审批：海外零留存合同与国内备案登记要和开发同时启动。

## 系统边界与部署关系

iOS 客户端按账户归属区只接入一个区域；两个区域部署同一套服务，靠同一份代码和签名配置包保持一致，用户数据互不流动。

&#91;embedded content: 部署关系 · iOS、两个区域、三个内部工具\]

管理后台和测试台架都是内部工具：后台在两区各部署一套、只连本区 `admin-api`；测试台架只连两区的预发环境；两地共用的提示词、适配规则、音色表只通过 CI 生成的签名配置包下发。

## 选型约束（来自 PRD v2.6.5，v2.7 草案沿用）

选型首先要满足下表这些硬约束，其次才是开发效率；凡违反其中任一条的方案直接淘汰。

| 约束 | PRD 出处 | 对选型的直接影响 |
| --- | --- | --- |
| 国内与海外两套独立部署，不共享账户库与业务存储 | 9.3 | 同一套代码、两套环境；核心依赖必须在两个区域都有可用实现，不能只押一家仅海外可用的托管服务 |
| 第三方站点凭证只存本机 Keychain（`ThisDeviceOnly`），严禁出端 | 9.1.1 | 需登录来源的采集只能在 iOS 端完成；后端永远不具备代抓能力 |
| 同语种原文零篡改，逐单元 SHA-256 校验 | 6.1、12.1 | 后端须原样保存客户端提交的 `clean_text` 并按 `unit_id` 直读；端云两侧的 Unicode 规范化与拼接规则必须用同一份规格和同一组测试向量 |
| 外部模型走 ZDR，请求不带真实用户 ID | 9.1.2 | 海外 LLM 与 TTS 供应商必须能签零留存；编排层要有任务 ID 与用户 ID 的映射服务 |
| 后台常驻内存 ≤ 80 MB，Share Extension < 15 MB，总磁盘 ≤ 400 MB | 7.1、10.3 | iOS 端用原生 Swift，不引入跨平台运行时；本地库和音频缓存要能精确计量与淘汰 |
| TTFA P95：同语种 1.5 s，跨语种 2.8 s，热缓存 300 ms | 10.1 | 主帖快轨与评论编排并行；TTS 必须流式，端云之间用流式传输 |
| 国内审计日志留存 ≥ 6 个月；海外 24 小时内完成擦除 | 9.3 | 审计库与业务库物理隔离；所有业务数据按 `user_id` 可级联删除 |
| 配额核销、偏好参数、摘要回执走 HMAC 防重放 | 9.2.2 | 网关层统一做签名校验，不散落在各服务里 |
| 团队规模小，大部分代码由 AI 编码代理产出（PRD 7.3 提到根 `AGENTS.md`） | 推断 | 后端、管理后台、测试台架尽量用同一门语言和主流框架，类型系统要强，减少需要人工维护的基础设施 |

预期接入 Android 或 Web（2026-11-26 负责人决定），交付时间另定；契约、订阅权益、设备证明与推送从第一版起与平台无关；后端接口按平台中立设计，后续 Android 原生 Kotlin 接入不需要改协议。

## iOS 客户端选型

iOS 端推荐纯原生 Swift 6 + SwiftUI，最低系统从 PRD 的 iOS 16 上调到 iOS 18。跨平台框架（Flutter、React Native）淘汰：Share Extension 的 15 MB 内存上限、后台 80 MB 上限、WebKit 采集和音频引擎都在最依赖原生 API 的地方。

**为什么上调到 iOS 18。** 2026 年 8 月 iOS 16.7 在欧洲、英国等地占比约 1.7%–2.1%，全球主力是 iOS 26.x，其次是 iOS 18.7（约 10%）（[StatCounter](https://gs.statcounter.com/ios-version-market-share/all/europe)）。上调带来三项直接收益：Observation 框架（iOS 17）、可编程调用的 Translation 框架 `TranslationSession` 与语言包可用性查询（iOS 18，PRD 10.2 离线翻译兜底和 11.3“本机朗读可用性”都依赖它），以及少维护两代兼容分支。若必须保留 iOS 17，离线翻译在 17 上直接按“本机无语言包”处理。

| 层 | 推荐 | 不选 / 备选 | 理由与关键做法 |
| --- | --- | --- | --- |
| 语言与 UI | Swift 6（严格并发）+ SwiftUI；WebView 容器用 UIKit 桥接 | Flutter、React Native | 内存与后台约束只有原生能控住 |
| 状态与架构 | `@Observable` + 单向数据流，按功能拆 SPM 本地包 | TCA（备选） | 少一层依赖；AI 代理对原生写法更熟悉 |
| 共享核心包 | `ReaderCore`：`CanonicalPost`、确定性清洗、SHA-256（CryptoKit）、URL 校验 | — | 主 App 与 Share Extension 共用同一份实现；清洗规则另写规格与黄金测试向量，端云共用 |
| 网络 | `URLSession`（HTTP/2、TLS 1.3）；证书固定用 Info.plist `NSPinnedDomains` 写主备公钥 | Alamofire | 声明式固定自带备用公钥，轮换不必发版 |
| 请求签名与防刷 | CryptoKit HMAC + App Attest（DeviceCheck） | 把 HMAC 密钥写死在包里 | 密钥按登录会话下发；App Attest 挡住脱离 App 的批量盗刷（PRD 11.2.3） |
| 本地库 | GRDB + SQLCipher（AES-256 全库）；库密钥存 Keychain | SwiftData、Core Data | SwiftData 不支持全库加密；清空即删 Keychain 密钥再删文件 |
| 文件保护等级 | `completeUntilFirstUserAuthentication` | `complete` | 锁屏后台播放与预取要读库，`complete` 会在锁屏时读不到 |
| 音频缓存 | 每个切片 AES-GCM 加密落盘，LRU 索引放在加密库里，硬上限 100 MB | AVAssetDownloadTask | 自管理才能精确计量、按站点登出级联销毁 |
| 站点凭证 | Keychain `AfterFirstUnlockThisDeviceOnly`，不同步 | 保留 WebKit 默认持久 Cookie | 见“PRD 需修正”一节：WebKit 默认把 Cookie 写在自己的磁盘目录 |
| 需登录来源采集 | 单实例 `WKWebView` + `WKUserScript` 在隔离 `WKContentWorld` 提取 DOM，经消息通道回传 JSON；退后台即销毁 | — | 隔离内容世界防止页面脚本篡改提取结果 |
| 公开源直抓 | `URLSession` + 逐站适配器（优先官方 JSON 接口，其次 HTML 解析） | 在 Extension 里做全量 DOM 解析 | 适配规则做成签名 JSON，由管理后台下发，站点改版不必发版 |
| 播放引擎 | `AVAudioEngine` + `AVAudioPlayerNode`，主轨 TTS、提示音、本机语音汇入同一混音器，末级加限幅 | `AVQueuePlayer` | 配额中途耗尽要无缝切到本机语音，两路必须在一个引擎里对响度 |
| 本机离线语音 | `AVSpeechSynthesizer.write(_:toBufferCallback:)` 输出 PCM 进混音器 | 直接 `speak()` | 直接播放绕过引擎，响度和进度都不可控 |
| 离线翻译 | Translation 框架（iOS 18），先查语言包可用性 | 自带端侧翻译模型 | 包体和内存都承受不起 |
| 锁屏与线控 | `MPRemoteCommandCenter`（`nextTrack` / `previousTrack`）、`MPNowPlayingInfoCenter`；CarPlay 用音频类模板 | — | 锁屏隐私模式只是改写 NowPlaying 标题；CarPlay 需单独申请音频 App 权限 |
| 后台采集 | 音频后台模式下用 `URLSession` 预取；`BGAppRefreshTask` 仅做尽力而为的补充 | 以 `BGContinuedProcessingTask` 做静默预取 | 后者仅 iOS 26 可用，且是“前台发起、带系统进度 UI”的任务（[Apple](https://developer.apple.com/tutorials/data/documentation/backgroundtasks/bgcontinuedprocessingtask.md)），不适合静默预取 |
| Share Extension | SwiftUI 容器；与主 App 经 App Group 共享“待抓收件箱”（只存 URL 与状态），登录态经共享 Keychain 访问组判断 | 在 App Group 存任何凭证 | 对齐 PRD 9.1.1 |
| 登录 | AuthenticationServices（Sign in with Apple）+ 邮箱验证码 | — | 验证码邮件由后端发送，见后端一节 |
| 订阅 | StoreKit 2；后端用 App Store Server API 与服务器通知 V2 作为权益真相源 | RevenueCat（备选） | 配额账本在自己后端，只需要 Apple 的交易事实 |
| 崩溃与性能 | 海外 Sentry；国内自建 Sentry 或国内 APM；`beforeSend` 强制剔除正文、URL、Cookie | 国内用户上报到海外 SaaS | 崩溃数据也属个人信息，受数据驻留约束 |

MVP 已去掉视频音轨，PRD 8.3 里“原视频音轨混音”暂不需要实现，但混音器结构保留。

## 后端服务与云基础设施

后端推荐 TypeScript（Node.js 26 LTS）模块化单体，拆成 3 个独立部署的进程；国内跑在阿里云，海外跑在 AWS，同一份代码、两套配置。选 TypeScript 是为了让后端、管理后台、测试台架共用一门语言和一套类型定义；负载以等待 LLM 和 TTS 为主，Node 的异步 IO 足够支撑 100–2,000 QPS 的横向扩容。

**服务划分（不做微服务）**

1. `bff`：鉴权、HMAC 与防重放校验、`R_daily` 频控、配额校验、任务 ID 签发；对 App 暴露 REST + 一条 WebSocket 任务通道。
2. `orchestrator`：主帖快轨、评论选拔与排序、译制与校验、串场词溯源、机审、音色分配，把播报脚本逐段推给 `bff`。
3. `audio-worker`：调 TTS、响度校准与限幅（ffmpeg）、写对象存储、计算切片摘要、按段结算语音合成用量并核销统一额度池。

**计费（统一额度池，两层计量）**：文本生成、翻译、语音合成、神经语音合成等全部云端模型调用从同一个额度池扣点。`orchestrator` 与 `audio-worker` 每次调用结束后，按该渠道的实际计价口径（输入 / 输出 Token、万字符、语音 Token、音频时长）记录原始用量与分渠道成本，再按参数化费率系数实时折算为用户点数，与余额在同一事务里原子核销。主备渠道对同一内容的折算差异 ≤ 10%，容错切换不加价。

管理后台的 API 是第 4 个进程，走独立域名和独立数据库账号，见管理后台一节。

| 组件 | 推荐 | 国内区域 | 海外区域 | 说明 |
| --- | --- | --- | --- | --- |
| Web 框架 | Fastify + zod | 同 | 同 | zod 定义生成 OpenAPI，再用 Apple 的 swift-openapi-generator 生成 iOS 客户端，接口契约只有一份 |
| 客户端到云的流式通道 | WebSocket 传脚本与切片清单（`unit_id`、`H_i`、切片 URL、切片摘要、配额事件）；音频切片走签名 URL 下载 | 同 | 同 | 按句切片天然支持“播完当前语句再切本机”和逐片校验 |
| 异步任务 | BullMQ（Redis） | 同 | 同 | 热路径在进程内流式处理，只有重生成、删除、审计导出进队列；不用 Temporal，它为秒级任务增加的延迟和运维负担不划算 |
| 业务库 | PostgreSQL 18 + Drizzle ORM | 阿里云 RDS PostgreSQL | AWS RDS PostgreSQL | 额度账本分两层：底层记每次调用的原始用量与渠道成本，用户侧只追加流水 + 幂等键（任务 ID + 阶段 + 序号），余额行加行锁在同一事务里扣点 |
| 缓存与频控 | Redis 7 兼容 | 阿里云 Redis 开源版 7.0 | ElastiCache（Valkey） | 任务状态、频控计数、防重放 nonce |
| 音频对象存储 | 公私两个独立 bucket，各自一把 KMS 密钥 | 阿里云 OSS | Cloudflare R2（经 Workers + Hono 边缘分发） | R2 不能在中国大陆创建 bucket（[Cloudflare](https://developers.cloudflare.com/china-network/reference/available-products)），国内必须换 OSS |
| 私有缓存 TTL | 播放确认后主动删除 + 每分钟清扫任务；生命周期规则只作兜底 | 同 | 同 | 对象存储生命周期按天生效，实现不了分钟级 `T_priv_ttl` |
| 审计日志 | 独立存储、独立密钥、独立访问账号 | 阿里云 SLS 独立 Project，留存 ≥ 180 天 | 不留正文，只留删除与权益事件 | 业务日志在应用层统一脚敏，不靠人工自觉 |
| 密钥 | KMS + 信封加密 | 阿里云 KMS | AWS KMS | HMAC 会话密钥、私有 bucket 密钥、任务 ID 映射表密钥分开管理 |
| 计算与部署 | 容器镜像，一份构建两地发布 | 阿里云 SAE（Serverless 应用引擎） | AWS ECS Fargate | 不自己维护 Kubernetes；两者都支持长连接 |
| 基础设施即代码 | Pulumi（TypeScript） | 阿里云 Provider | AWS Provider | 两套环境用同一份堆栈定义，避免两地配置漂移 |
| 验证码邮件 | 事务邮件服务 | 阿里云邮件推送 | Resend 或 SES | 邮箱地址属个人信息，不跨区发送 |
| 订阅权益 | App Store Server API + 服务器通知 V2 | 同 | 同 | 通知接收端按账户归属区分别配置 |

**响度处理的做法。** 不对每个切片做两遍响度归一化，否则每一句都要等整段生成完，压不住 1.5 s 的 TTFA。改为离线为每个音色标定增益，在线只做固定增益加真峰值限幅；标定和复核放在测试台架里。

**国内上线的基础设施前提。** 域名 ICP 备案、App 备案、公安联网备案都要在提审前完成；是否需要等保测评，由合规负责人确认。

## AI 与语音供应商

两个区域各接一套供应商，代码里统一经过一层自建的薄模型网关（基于 Vercel AI SDK 的 provider 接口，国内大模型多为 OpenAI 兼容接口，可直接接入）。网关负责任务 ID 替换用户 ID、随机边界包裹、结构化输出校验、超时与备用线路切换，业务代码不直接调供应商 SDK。

| 能力 | 国内区域 | 海外区域 | 关键约束 |
| --- | --- | --- | --- |
| 评论选拔、排序、串场词 | 豆包（火山方舟）或通义千问（阿里云百炼），必须是已备案模型 | Claude（Anthropic API 开 ZDR，或 Amazon Bedrock） | 只输出 `unit_id` 顺序、情绪枚举和受限句式，用结构化输出约束 |
| 逐条口语精译 `VerbatimTranslator` | 同上，低温度，独立调用 | 同上 | 不与选拔共用上下文 |
| 译文语义一致性校验 | 与翻译不同厂商或不同型号 | 同 | 同一个模型自己校自己，错误高度相关，容易一起漏过 |
| 主轨 TTS | 豆包语音合成 2.0（流式、支持情绪与指令控制）；备用：阿里云 CosyVoice | ElevenLabs；备用：Google Cloud TTS 或 Azure Speech | 备用线路要在 `T_tts_timeout` 内切换，两家都要做各音色的响度标定 |
| 出声前内容机审 | 阿里云内容安全或火山引擎内容安全（文本审核） | OpenAI Moderation 或 LLM 分类器 | 国内机审覆盖所有待播文本，含译文和串场词 |
| 显式合成标识 | 预录的固定语音提示片段，作为客户端内置资源 | 同 | 不走每次 TTS，不耗额度，内容与位置可控 |
| 隐式标识与水印 | 音频文件元数据写入生成方与内容编号；自嵌统一水印（开源 AudioSeal，两区相同），保留厂商自带水印（如 SynthID）作为补充；待合规确认 | 与国内相同（2026-11-26 负责人决定）：元数据隐式标识 + 数字水印，机器可读、可检测，兼顾欧盟 AI 法案第 50 条 | 水印必须在响度限幅之后嵌入，否则会被削掉 |

**海外零留存（ZDR）的现状，决定了供应商要尽早谈。**

- Anthropic：ZDR 需要销售审核，按组织开通（[Anthropic](https://privacy.claude.com/en/articles/8956058-i-need-to-sign-a-baa-with-anthropic-what-should-i-do)）。结构化输出属“有条件可用”：提示词与输出不存，但 JSON schema 会缓存到最后一次使用后 24 小时；批处理接口不支持 ZDR（[Anthropic 文档](https://platform.claude.com/docs/en/build-with-claude/api-and-data-retention)）。本产品的 schema 只含字段名和枚举常量，不含用户数据，可以接受；批处理禁用。Fable 5 / Mythos 5 这类需 30 天留存的模型不进这条链路。
- 走 Amazon Bedrock 时数据处理方是 AWS，留存条款看 AWS 一侧（同一份 Anthropic 文档）；后端本来就在 AWS，这是合同路径最短的选项，需书面确认。
- OpenAI：ZDR 同样需要事先审批（[OpenAI](https://developers.openai.com/api/docs/guides/your-data/index.html)）。
- ElevenLabs：零留存模式只对部分企业客户开放，且开启后官方无法协助排查合成问题（[ElevenLabs](https://elevenlabs.io/docs/eleven-api/resources/zero-retention-mode/llms.txt)）。拿不到时改用备用 TTS 作为主线路。

**国内备案与登记。** 通过 API 调用已备案模型的应用，由地方网信办登记；上线后要在显著位置公示所用模型名称与备案号或上线编号（[央视网](https://m.gmw.cn/2026-07/10/content_1304528476.htm)）。因此 App 设置里要有“模型与备案信息”页，内容由管理后台配置，换供应商时同步更新。豆包与千问的具体备案编号、TTS 是否另需登记，由合规负责人确认。

## 管理后台选型

管理后台推荐 React + Vite 单页应用，用 Refine 做列表、表单、权限的骨架，Ant Design 5 做组件；在两个区域各部署一套，各连各的数据。后台是内部工具，不需要 SEO 和服务端渲染，Next.js 的额外部署复杂度没有收益。

**功能范围（从 PRD 反推）**

| 模块 | 做什么 | 对应 PRD |
| --- | --- | --- |
| 账户与删除工单 | 按账户查状态、归属区、注销与擦除进度；海外 24 小时时限倒计时 | 7.1、9.3 |
| 订阅与配额 | `Q_free / Q_plus / Q_pro`、`R_daily` 与费率系数、渠道单价（只读）；查额度流水（可按渠道 × 计价单位展开原始用量与成本）；单笔补偿必须填原因 | 11 |
| 来源适配器 | 公开白名单（决定能否进公共缓存）、逐站提取规则版本、签名发布与灰度 | 7.1、9.1.3 |
| 预置样帖 | 上传预生成音频与脚本、排序 | 7.1、7.3 |
| 模型、音色与提示词 | 供应商路由、音色表与情绪映射、提示词版本；只能发布已通过测试台架门禁的版本 | 6、8.2 |
| 合规 | 出声前安全检查拦截记录（两区；国内仅合规角色）、合成标识提示音版本、模型备案公示信息 | 9.3 |
| 运营指标 | 完播率、TTFA P95、`η_pub` 命中率、每分钟合成成本、降级次数 | 2.2、10 |
| 风控 | App Attest 失败、频控命中、异常用量账户 | 11.2.3 |

**技术栈**

| 层 | 推荐 | 说明 |
| --- | --- | --- |
| 前端 | React 19 + Vite + Refine + Ant Design 5 + TanStack Query | 表格和表单密集，Refine 省掉大量样板代码；Ant Design 中文生态最完整 |
| 图表 | ECharts | 运营指标页够用 |
| API | 独立的 `admin-api` 进程，Fastify + zod，与后端共用类型包 | 不复用 `bff` 的路由，攻击面分开 |
| 登录 | Passkey（WebAuthn）+ 强制二次验证；前面再加一层零信任网关（海外 Cloudflare Access，国内阿里云 IDaaS 或 IP 白名单） | 后台账号与 App 账号完全分开 |
| 权限 | RBAC：运营、客服、合规审核、发布者、超级管理员 | 现在只有一个人也先分角色，审计才有意义 |
| 数据库权限 | `admin-api` 使用独立数据库角色，对 `clean_text`、私有缓存索引、国内审计库没有读权限 | PRD 9.3 要求审计库禁止业务与运营侧读取，用数据库权限实现，不靠接口过滤 |
| 操作审计 | 每次写操作记录操作人、对象、前后值，只追加 | 配额补偿与配置发布必须可追溯 |
| 部署 | 静态文件放各自区域的对象存储与 CDN，`admin-api` 与后端同集群不同服务 | 国内后台访问国内用户数据必须留在境内，不能合并成一个全球后台 |

**跨区配置用“配置即代码”。** 提示词、来源适配规则、音色表这类两地共用的配置存在 Git 仓库，CI 跑完测试台架门禁后打成签名配置包；两地后台只做“发布某个版本 / 回滚”，不在线编辑。这样两地不会各改各的，也不需要跨境同步数据库。只属于本区的数据（账户、配额、拦截记录）才在后台直接操作。

## 后端 Web 测试台架选型

测试台架定位为“不经过 iOS、直接驱动后端整条流水线”的内部 Web 工具，同时是 PRD 第 12 节上线门禁的执行器。它只跑在预发环境，只用固定样本和合成数据，不接触生产用户数据。

**能力清单**

| 能力 | 做法 | 服务于 |
| --- | --- | --- |
| 单帖调试 | 输入 `CanonicalPost` JSON 或样本编号，选区域、档位、偏好、目标语言，逐步展示清洗结果与 `H_i`、选拔输出、译文与校验结论、机审结果、音色分配，每段音频可试听 | 日常开发 |
| 时延时间线 | 每个阶段的 OpenTelemetry span 画成甘特图，标出首段音频出口时刻 | TTFA P95 的 1.5 s / 2.8 s 目标 |
| 样本库 | 公开源、需登录来源、跨语种、对抗注入四类样本，按版本存在 Git，每条带期望结果 | PRD 12 开头的评测集要求 |
| 确定性门禁 | 摘要核验 100%、回复关系错配 0%、相邻同音色 0%、配额为 0 时云端合成调用 0 次 | 12.1、12.2、12.6、12.7 |
| 模型类门禁 | 注入拦截、翻译极性与实体保持、串场词溯源，用 promptfoo 跑；红队用例与自定义断言写成配置 | 12.1、12.3 |
| 合规门禁 | 国内违规样本（含海外跨语种样本）出声前拦截率 | 12.5 |
| 音频质量 | 用 ffmpeg 的 EBU R128 滤镜测每个音色的 LUFS 与真峰值，生成增益标定表；波形用 wavesurfer.js 显示 | 8.3、12.6 |
| 变更对比 | 同一批样本在两个提示词版本或两家供应商之间并排对比，输出差异与成本 | 管理后台“只发布已过门禁的版本” |

**技术栈**

| 层 | 推荐 | 说明 |
| --- | --- | --- |
| 前端 | React + Vite，与管理后台共用组件库（Ant Design） | 一套 UI 代码，两个入口 |
| 驱动方式 | 直接调用后端的流水线模块（同一 monorepo 的包），也可以以模拟客户端身份走完整 `bff` 接口 | 前者看中间产物，后者验端到端，包括 HMAC 与配额 |
| 中间产物存储 | 预发环境自己的 PostgreSQL，按运行批次存每步输入输出 | MVP 不自建 Langfuse：它自托管要连 ClickHouse 一起运维（[Langfuse](https://langfuse.com/self-hosting.md)），对小团队偏重 |
| 模型评测 | promptfoo（MIT，2026 年 3 月已并入 OpenAI，仍保持开源） | [项目说明](https://github.com/DeepDocs-eval/promptfoo)；核心评测可在本地跑，样本不出机器 |
| 确定性测试 | Vitest（TypeScript）+ 同一份黄金向量在 iOS 侧用 Swift Testing 跑 | 清洗与摘要的端云一致性靠两边跑同一组向量来保证 |
| CI 集成 | GitHub Actions：每次合并跑确定性门禁；提示词或供应商变更时加跑模型类门禁；通过才生成签名配置包 | 与管理后台的发布流程接在一起 |
| 访问控制 | 与管理后台同一套零信任网关与 Passkey 登录 | 台架能直接花模型与 TTS 的钱，必须限人限额 |

国内区域的模型与机审供应商不同，模型类门禁要在两个区域的预发环境各跑一遍；样本库是公开或合成数据，可以两地共用。

## 风险与待决策项

最大的风险不在技术实现，而在外部等待时间：海外零留存合同和国内备案登记都不由我方控制，应与开发并行启动。

| 事项 | 为什么要尽早定 | 建议 |
| --- | --- | --- |
| 海外 LLM 与 TTS 的零留存合同 | 各家都需要审批，ElevenLabs 只对部分企业客户开放；拿不到就违反 PRD 9.1.2 | 现在就提交申请；LLM 优先走 Bedrock；TTS 准备一家备选作为可能的主线路 |

| 仅音频提示作为合成标识 | PRD 9.3 已列为待确认 | 保持待确认；两区同样处理（显式 + 隐式标识 + 水印）；技术上提示音做成可热更新的内置资源，结论变了也不必发版 |

## 分阶段落地建议

先把端云契约和测试台架做出来，再做 iOS 主链路；代码从第一天就按两个区写，哪个区先上线由备案与合同进度决定。每个阶段以测试台架上的门禁通过为结束标志。

1. **并行启动的外部事项**：提交海外零留存申请；选定国内 LLM 与 TTS 并启动应用登记；域名 ICP 与 App 备案；申请 CarPlay 音频权限。
2. **契约与测试台架**：monorepo 搭建；清洗与摘要规格及黄金向量（TS 与 Swift 两侧都跑）；OpenAPI 契约与 Swift 客户端生成；测试台架单帖调试与时延时间线。
   - 门禁：摘要核验 100%、回复关系错配 0%（12.1 确定性部分、12.2）。
3. **同语种主链路**：iOS 登录、Share Extension、公开源直抓、加密本地库、播放引擎与线控；后端 `bff`、`orchestrator`、`audio-worker` 的分支 A；配额账本与 StoreKit 2。
   - 门禁：同语种 TTFA P95 ≤ 1.5 s、相邻同音色 0%、配额拦截门禁（12.6、12.7）。
4. **跨语种、需登录来源与管理后台**：分支 B 译制与校验；WebKit 采集与凭证方案；离线语音与离线翻译兜底；管理后台第一版（配额、适配器、样帖、配置发布、删除工单）。
   - 门禁：注入拦截 100%、凭证与缓存隔离各项为 0、跨语种 TTFA P95 ≤ 2.8 s（12.3、12.4）。
5. **第二区域上线**：用同一份 Pulumi 堆栈拉起另一个区；接该区供应商；国内区加上机审与审计库（合成标识两区相同，第一个区上线时即具备）。
   - 门禁：国内出声前机审拦截 100%（12.5），备案与登记完成。

## 1. 总体结论与技术栈总表

整体采用“iOS 原生 + 其余全部 TypeScript”的双语言技术栈：一个 pnpm Monorepo 承载后端、管理后台、测试台架与共享契约，iOS 工程放在同一仓库的 `apps/ios`。后端以容器镜像形式同时发布到阿里云（国内区）与 AWS（海外区），两区数据物理隔离，共享配置只通过 CI 签名的配置包下发。

### 1.2 五条关键架构决策

1. **契约单一信源。** API 以 zod schema 定义，生成 OpenAPI，再生成 Swift 客户端；清洗与摘要规则以规格文档 + 黄金向量定义，Swift 与 TS 两侧都对向量跑测试。
2. **模块化单体，多进程部署。** 一个后端代码库拆成 `bff`、`orchestrator`、`audio-worker`、`admin-api` 四个可独立伸缩的进程，不做微服务。
3. **热路径不进队列。** 单帖生成在进程内以流式管线完成，队列只用于重生成、删除、导出等可延迟任务，以保证 TTFA。
4. **两区同构、数据不通。** 同一镜像、同一 Pulumi 堆栈定义，按区注入配置；不存在跨区数据库复制或全球后台。
5. **配置即代码。** 提示词、结构化输出 schema、站点提取规则、音色表存 Git，过测试台架门禁后打成签名配置包，管理后台只做发布与回滚。

## 2. 系统总体架构

每个区域是一套完整、自治的部署单元：边缘入口 → 4 个应用进程 → PostgreSQL / Redis / 对象存储 → 区内外部供应商。客户端只与自己账户归属区的入口通信，进程间通过 Redis Streams 传递任务与事件。

右列是用户请求路径，左列是管理平面与存储。`bff` 到 `orchestrator`、`orchestrator` 到 `audio-worker` 都经 Redis Streams；只有右侧三个后台进程会访问外部供应商。

### 2.2 信任边界

1. **设备不可信。** 服务端不信任客户端上报的任何“免扣”“离线”状态（PRD 11.2.2）；第三方站点凭证只存在这一侧。
2. **区域边缘。** WAF + 负载均衡终结 TLS，只放行到 `bff`；`orchestrator`、`audio-worker` 没有公网入口。
3. **区内私有网络。** 数据库、Redis 只在私有子网；各进程使用不同的数据库角色。
4. **外部供应商。** 只发送任务 ID 与必要文本，海外走 ZDR 通道。
5. **管理平面。** 后台与测试台架只能经零信任网关访问，与用户流量入口分开。

### 2.3 区域路由

账户在注册时绑定 `home_region`（PRD 9.3），之后客户端固定访问该区入口域名。问题是登录前客户端不知道该连哪个区，而跨区查询“这个邮箱在哪个区”本身就是一次个人信息跨境。建议方案：

- 默认区按 App Store 店面国家（StoreKit `Storefront.countryCode`）决定：中国大陆店面连国内区，其余连海外区。
- 登录页提供显式切换“中国大陆账号 / 海外账号”，不做跨区自动查找。
- 登录成功后把 `home_region` 与区域入口域名写入 Keychain，之后不再随网络出口 IP 变化。

### 3.3 依赖规则

- `packages/*` 不依赖 `apps/*`；`apps/*` 之间不互相依赖，共享代码下沉到 `packages/`。用 Turborepo 的依赖图和 Biome 的导入规则强制。
- 后端模块之间只通过各模块的 `index.ts` 公开接口调用，不跨模块直接读写对方的表。
- 新增第三方依赖需要写进 ADR 或 PR 说明：许可证、维护状态、体积、替代方案。iOS 端目标是不超过 5 个外部包。

新增、升级或移除任何依赖，都要先过 `05-toolchain-and-resources.md` §2 的准入检查（许可证、维护状态、数据外发、体积）并写依赖 ADR。同一职责只允许一个库：HTTP 客户端只用 `undici`，ORM 只用 Drizzle，iOS 存储只用 GRDB。

## 4. 端云契约

端云之间只有三类契约：REST API（请求—响应）、WebSocket 任务流（脚本与切片推送）、`CanonicalPost` 数据模型及其清洗摘要规格。三者都在 `packages/contracts` 与 `packages/canonical-spec` 中维护，是唯一信源。

### 4.1 REST API（`https://api.<region-domain>/v1`）

| 方法 路径 | 用途 | 备注 |
| --- | --- | --- |
| `POST /auth/apple` | Sign in with Apple 登录 / 注册 | 服务端校验 Apple identity token；首次注册时写入 `home_region` |
| `POST /auth/email/code` | 发送 6 位邮箱验证码 | 同一邮箱 2 分钟内不可重发（PRD 7.3） |
| `POST /auth/email/verify` | 校验验证码并登录 | 错误次数限制 |
| `POST /auth/refresh` · `POST /auth/logout` | 刷新 / 吊销会话 | 刷新令牌轮换 |
| `POST /attest/challenge` · `POST /attest/verify` | App Attest 挑战与验证 | 绑定设备密钥与会话 |
| `GET /me` | 档位、剩余配额、`home_region`、功能开关 |  |
| `DELETE /account` | 自助注销与数据删除 | 异步执行，返回工单号（PRD 7.1、9.3） |
| `POST /jobs` | 创建生成任务：`CanonicalPost` + 偏好 + `target_lang` | 必须带 `Idempotency-Key`；返回 `job_id` 与流地址；配额为 0 时返回 `QUOTA_EXHAUSTED`，客户端展示 11.3 拦截层 |
| `GET /jobs/{id}` · `POST /jobs/{id}/cancel` | 查询 / 取消任务 |  |
| `POST /jobs/{id}/ack` | 播放确认 | 触发私有缓存删除 |
| `GET /samples` | 预置样帖列表与静态音频地址 | 不扣配额 |
| `GET /config/bundle` | 当前生效的签名配置包（站点规则、白名单、开关） | 客户端验签后生效 |
| `POST /subscriptions/sync` | 上报 StoreKit 2 交易 JWS | 服务端再向 App Store Server API 核实 |
| `POST /webhooks/app-store` | App Store Server Notifications V2 | Apple 调用，验证 JWS 签名 |

**通用约定**

- 错误体采用 RFC 9457（`application/problem+json`），附加稳定的 `code`：`AUTH_EXPIRED`、`AUTH_REVOKED`、`SIGNATURE_INVALID`、`REPLAY_DETECTED`、`RATE_LIMITED`（只表示令牌桶频控）、`DAILY_LIMIT`（当日次数上限 `R_daily`，带 `resetAt`）、`QUOTA_EXHAUSTED`、`REGION_MISMATCH`、`CONTENT_BLOCKED`、`UPSTREAM_DEGRADED`、`SERVICE_PAUSED`、`BRANCH_DISABLED`、`SITE_RULE_DISABLED`、`VALIDATION_FAILED`、`CLIENT_TOO_OLD`（426，只有 `GET /me` 例外）。
- 版本：路径带 `/v1`，v1 内只做加法。客户端带 `X-Client-Version`，低于服务端最低支持版本时返回 426 + `CLIENT_TOO_OLD`。
- 所有写接口带请求签名头（见第 10 节）；`POST /jobs` 的幂等键在服务端保留 24 小时。

### 4.2 WebSocket 任务流（`wss://api.<region-domain>/v1/stream`）

一条连接可以订阅多个任务。服务端消息带单调递增的 `seq`，断线重连后发 `resume(job_id, last_seq)` 续传；服务端从 Redis Stream 补发丢失的消息。

| 方向 | 消息类型 | 关键字段 |
| --- | --- | --- |
| C→S | `hello` | `access_token`、`protocol_version` |
| C→S | `subscribe` / `resume` / `cancel` / `ping` / progress / seek / extend | `job_id`、`last_seq` |
| S→C | `job.accepted` | `job_id`、`branch`（`same_lang` / `translate`）、预计评论数 |
| S→C | `script.unit` | `unit_id`、`role`（主持 / 作者 / 评论者）、`voice_slot`、`emotion`、`lang`、`text_sha256`（服务端对送入 TTS 的文本重算）、`translated_text`（仅分支 B） |
| S→C | `segment.ready` | `seq`、`unit_id`、`url`、`expires_at`、`audio_sha256`、`duration_ms`、`bytes`、`cache_scope` |
| S→C | `quota.update` / `quota.exhausted` | `remaining_ms`；耗尽时给出最后一个已合成 `seq`，客户端播完后切本机语音（PRD 11.2） |
| S→C | `job.degraded` | `reason`（备用 TTS、译文被拦、机审拦截等） |
| S→C | `job.completed` / `job.failed` | 统计或错误 `code` |

### 4.3 `CanonicalPost` 数据模型

```ts
type CanonicalPost = {
  schemaVersion: 1;
  source: {
    site: string;             // 站点适配器 ID
    url: string;              // 规范化后的帖子 URL
    postId: string;
    fetchedAt: string;        // ISO 8601
    cacheScope: 'PUBLIC' | 'PRIVATE';
  };
  langHint?: string;          // BCP 47
  units: Unit[];              // units[0] 为主帖
};

type Unit = {
  unitId: string;             // 主帖固定为 "post"
  kind: 'post' | 'comment';
  authorId: string;           // 匿名或已注销：`anon:${unitId}`
  authorDisplay?: string;
  parentId?: string;
  parentConfidence: 'high' | 'low';   // low → 平铺播报（PRD 7.2）
  cleanText: string;
  likes?: number;             // 仅用于离线降级排序，不在 UI 展示
  hasImages: boolean;
  hasVideo: boolean;
  hash: string;               // H_i，小写 hex
};
```

### 4.4 清洗与摘要规格（`packages/canonical-spec/SPEC.md`）

**确定性清洗步骤（顺序不可变）**

1. 解码 HTML 实体。
2. Unicode 规范化为 NFC。
3. 删除 C0/C1 控制字符（保留 `\n`）、BOM、U+200B、U+2060、双向控制符 U+202A–U+202E 与 U+2066–U+2069。
4. U+200C / U+200D（零宽非连接符 / 连接符）仅在两侧都是 emoji 或属于语言文字连写时保留，其余删除；否则会打碎“家庭”类组合 emoji。
5. 换行统一为 `\n`，连续空行折叠为 1 个，首尾空白去掉。
6. 不在清洗阶段转义 `<`、`&` 等字符；SSML 转义放在 TTS 输入边界。这一条与 PRD 6.1 “清洗时转义语音合成控制标签”的写法不同，目的是让 `clean_text` 保持原文字面，需与产品确认。

**摘要算法**

```latex
H_i = \mathrm{SHA256}\big(\mathrm{lp}(\mathit{unitId}_i) \,\|\, \mathrm{lp}(\mathit{authorId}_i) \,\|\, \mathrm{lp}(\mathit{cleanText}_i)\big)
```

其中 lp(x) = 4 字节大端长度 + x 的 UTF-8 字节，输出小写 hex。长度前缀用来消除拼接歧义（例如 `"ab" + "c"` 与 `"a" + "bc"` 的拼接结果相同）。

**黄金向量。** `vectors/*.json` 每条包含 `raw`、`expectedClean`、`unitId`、`authorId`、`expectedHash`，覆盖：CJK、阿拉伯文双向文本、组合 emoji、各类零宽字符、HTML 实体、全角空格、超长文本、空串。Swift 与 TS 两侧 CI 都必须 100% 通过。任何规则变更都要升级 `schemaVersion` 并新增向量。

## 5. iOS 客户端：分层架构与模块

iOS 工程分五层，依赖只能自上而下：App（组装与导航）→ Features（页面）→ Domain（业务服务）→ Infrastructure（系统能力封装）→ `ReaderCore`（纯逻辑，无任何依赖）。每层是一个或多个 SPM 本地包；主 App 与 Share Extension 只是两个不同的组装入口。

### 5.1 分层与包

| 层 | 包 | 主要类型 | 依赖 | 测试方式 |
| --- | --- | --- | --- | --- |
| Core | `ReaderCore` | `CanonicalPost`、`Unit`、`Cleaner`、`UnitHasher`、`URLGuard`、站点规则模型 | 无（仅 Foundation、CryptoKit） | 对黄金向量的单元测试 |
| Infra | `Storage` | `AppDatabase`（GRDB `DatabasePool`）、`AudioCache`、`KeychainStore`、`SharedInbox` | GRDB + SQLCipher | 临时加密库上的集成测试 |
| Infra | `Networking` | `APIClient`（生成）、`RequestSigner`、`JobStreamClient`（WebSocket）、`AttestService` | swift-openapi-runtime / URLSession transport | 本地 mock server |
| Infra | `Capture` | `DirectFetcher`、`WebCaptureController`（单例 WKWebView）、`SiteAdapterRuntime` | WebKit、HTML 解析库 | 录制的页面 fixture |
| Infra | `Audio` | `PlaybackEngine`（AVAudioEngine）、`LocalSpeech`（AVSpeechSynthesizer）、`OfflineTranslator`、`NowPlayingBridge` | AVFoundation、MediaPlayer、Translation | 离线渲染模式校验电平 |
| Infra | `Commerce` | `StoreService`（StoreKit 2）、`AuthService`（Sign in with Apple、邮箱验证码） | StoreKit、AuthenticationServices | StoreKit 配置文件本地测试 |

### 5.2 依赖注入与状态管理

- Domain 服务只依赖协议（`protocol`），在 App 层的 `AppEnvironment` 中组装真实实现，并通过 SwiftUI `Environment` 下传；测试与 SwiftUI 预览注入假实现。不引入第三方 DI 框架。
- 每个页面一个 `@Observable @MainActor` 的 Model：视图只读状态、只调用 Model 的方法；Model 调用 Domain 服务。跨页面共享状态（当前播放、登录态、配额）由对应服务持有并暴露为 `@Observable`。
- 导航用 `NavigationStack`；搜索、通知、播放列表用 `.sheet` + `presentationDetents([.medium, .large])` 实现 PRD 7.3 的半屏 / 全屏底部弹层。

### 5.3 并发模型（Swift 6 strict concurrency）

| 组件 | 隔离方式 | 原因 |
| --- | --- | --- |
| 页面 Model、`PlaybackCoordinator`、`QuotaService` 对外状态 | `@MainActor` | UI 状态单线程修改 |
| `JobStreamClient` | `actor` | 管理 WebSocket 连接、重连、`last_seq`；对外暴露 `AsyncThrowingStream<JobEvent>` |
| `WebCaptureController` | `@MainActor` + 串行队列 | WKWebView 必须在主线程；单实例，抓取请求排队 |
| `AudioCache`、`SegmentDownloader` | `actor` | 并发下载、LRU 淘汰与容量计量需互斥 |
| `AppDatabase` | GRDB `DatabasePool`（WAL，多读单写） | 读写并发安全由库保证 |
| `PlaybackEngine` | 独占一个串行执行器 | AVAudioEngine 的调度与中断处理要在同一上下文完成 |

跨边界传递的模型一律是值类型并声明 `Sendable`。事件链路为：`JobStreamClient` → `JobService`（校验摘要、触发下载）→ `PlaybackCoordinator`（排队、切换本机语音）→ `PlaybackEngine`。

## 6. iOS 客户端：关键子系统设计

### 6.1 采集管线

队列项的采集状态机：`queued → fetching → captured → ready`；异常分支为 `pending_foreground`（需网页引擎但当前在后台）、`needs_site_login`、`adapter_failed`、`blocked_url`。

- **站点适配器**：配置包中的每个站点规则声明 `matchHosts`、`mode`（`direct_json` / `direct_html` / `webview`）、字段选择器或 JSON 路径、回复关系解析方式、分页策略。规则是数据，不是可执行代码；`webview` 模式使用随 App 发布的固定提取脚本，配置只提供选择器，避免下发任意 JS。
- **直抓**：专用 `URLSession`（ephemeral 配置，不写 Cookie）、重定向 ≤ 3 次、响应体上限（建议 2 MB）、每次重定向都重新过 `URLGuard`（拒绝环回、私网、链路本地、组播地址，并在 DNS 解析后再校验 IP 防 DNS rebinding）。
- **网页引擎**：`WKWebsiteDataStore.nonPersistent()`；抓取前从 Keychain 注入该站 Cookie，登录成功后从 `httpCookieStore` 导出回 Keychain；提取脚本跑在独立 `WKContentWorld`，经 `WKScriptMessageHandler` 回传；超时 15 s；进后台立即 `removeFromSuperview` 并释放。
- **预取**：前台亮屏时对队列后续 `N_pre` 篇、每篇 `C_batch` 条评论预取；音频后台播放时只预取可直抓的来源（PRD 7.4）。

### 6.2 Share Extension

- 入口用 SwiftUI 容器；从 `NSExtensionItem` 取 URL；通过共享 Keychain 访问组判断登录态。
- 未登录：不写收件箱、不联网，提示打开 App（iOS 无公开 API 从扩展拉起宿主 App）。
- 已登录 + 公开源：2.5 s 预算内直抓并清洗，超时则降级为只入收件箱；已登录 + 需登录源：只写链接与状态。
- 收件箱是 App Group 容器内的一个小型 SQLCipher 库，密钥在共享 Keychain；主 App 启动、回到前台时消费并清空。扩展内用 Instruments 内存图确认峰值 < 15 MB。

### 6.3 本地数据库结构（GRDB + SQLCipher）

| 表 | 主要字段 | 说明 |
| --- | --- | --- |
| `queue_item` | `id`、`post_key`、`position`、`capture_state`、`added_at` | 播放队列与采集状态 |
| `post_snapshot` | `post_key`、`site`、`url`、`cache_scope`、`canonical_json`、`captured_at`、`favorited`、`compact_after` | 未收藏快照 30 天后压缩为元数据 |
| `unit_hash` | `post_key`、`unit_id`、`hash` | 播放前校验用的本地摘要 |
| `audio_segment` | `version_key`、`seq`、`unit_id`、`file`、`bytes`、`audio_sha256`、`duration_ms`、`last_played_at`、`site` | LRU 索引；`version_key` = 帖子 + 偏好 + 语种 + 音色版本，用来判断“同一生成版本”（复听免费） |
| `playback_progress` | `post_key`、`seq`、`offset_ms` | 断点续播 |
| `site_session` | `site`、`logged_in`、`updated_at` | 只记状态，凭证本体在 Keychain |
| `config_bundle` | `version`、`signature`、`payload`、`activated_at` | 已验签的配置包 |
| `setting` | `key`、`value` | 偏好、`target_lang`、`passthrough_langs`、锁屏隐私开关 |

迁移用 GRDB `DatabaseMigrator`，只增不改。库密钥为首启随机 32 字节，存 Keychain（`ThisDeviceOnly`）；库文件保护等级 `completeUntilFirstUserAuthentication`。登出 / 一键清理：关闭连接 → 删 Keychain 密钥 → 删库文件与音频目录。

### 6.4 播放引擎

**音频图**：三个 `AVAudioPlayerNode`（云端 TTS 切片、提示音、本机语音 PCM）→ `AVAudioMixerNode` → Apple Peak Limiter（`AVAudioUnitEffect`）→ 输出。本机语音用 `AVSpeechSynthesizer.write(_:toBufferCallback:)` 取 PCM 再排入节点，保证与云端声音经过同一限幅器。

- **切片格式**：AAC-LC、单声道、48 kbps 左右、`.m4a`，系统原生解码；一句一个切片。
- **停顿**：说话人交替 200 ms、议题切换 350 ms、叙事留白 550 ms（PRD 8.1）由客户端按脚本插入静音缓冲，不烧进切片，切片因此可以跨帖复用。
- **缓冲**：维持 ≥ 10 s 已下载并校验通过的音频（PRD 10.1）；校验失败立即停止并上报完整性告警。
- **音频会话**：`AVAudioSession` 类别 `.playback`、模式 `.spokenAudio`；处理中断（来电）与路由变化（拔耳机即暂停）。
- **线控**：`MPRemoteCommandCenter` 的 `togglePlayPause`、`nextTrack`、`previousTrack`；`previousTrack` 内按 `T_prev_guard`（默认 3 s）判断回上一章节或倒退 15 s。
- **锁屏隐私**：`MPNowPlayingInfoCenter` 在隐私模式下只写通用标题与 App 图标。
- **CarPlay**：`CPNowPlayingTemplate` + `CPListTemplate`（队列），需申请 `com.apple.developer.carplay-audio` 权限。

### 6.5 后台运行

- `UIBackgroundModes: audio`：播放期间进程常驻，在此期间做直抓预取与切片下载。
- `BGAppRefreshTask`：未播放时尽力而为地预取，不作为可验收能力。
- `BGContinuedProcessingTask` 仅 iOS 26 可用且需用户前台发起、带系统进度 UI（[Apple](https://developer.apple.com/tutorials/data/documentation/backgroundtasks/bgcontinuedprocessingtask.md)），本产品不使用。
- 后台内存预算 `M_bg_ram` ≤ 80 MB：后台不持有 WKWebView、不解码图片、音频缓冲上限固定。

### 6.6 离线与降级决策

1. 有云端脚本 → 按脚本顺序用本机语音读入选单元；无脚本 → 按 `likes` 降序取头部；无赞数或全为 0 → 按原顺序、去掉超短重复句后取前 `N_brief` 条，并先播降级提示音（PRD 10.2）。
2. 语种判定：源语种 = `target_lang` 或在 `passthrough_langs` → 直接读；否则 `LanguageAvailability` 查询语言包，`installed` → `TranslationSession` 译后读；否则播提示并跳到下一篇。
3. 本机朗读不扣配额；是否“服务端确认故障”由服务端状态接口或 `job.degraded` 决定，客户端不自报免扣。

### 6.7 配额拦截与订阅（PRD 11.3）

- `POST /jobs` 返回 `QUOTA_EXHAUSTED` → 弹出 `QuotaGate` 弹层：升级（下一档 `Product`）、用本机语音朗读（按 6.6 第 2 条判断可用性）、取消。预置样帖与已缓存 `version_key` 不走这条路径。
- StoreKit 2：`Product.products(for:)` → `purchase(options: [.appAccountToken(userUUID)])` → 把交易 JWS 发给 `POST /subscriptions/sync` → 成功后自动重发原 `POST /jobs`。App 启动即监听 `Transaction.updates`，处理续订、退款与家庭共享。

## 8. 后端：技术栈与服务架构

后端是一个 TypeScript 模块化单体（`apps/server`），打成一个镜像，用不同启动命令跑成 4 种进程；进程间通过 Redis Streams 通信，持久状态在 PostgreSQL。

### 8.1 语言与框架选型

| 候选 | 优势 | 劣势 | 结论 |
| --- | --- | --- | --- |
| **TypeScript / Node.js 26** | 异步 IO 适合“等模型、等 TTS”的负载；与后台、台架、契约共用类型；AI SDK 生态最全；AI 代理生成质量高 | CPU 密集任务弱（音频处理交给 ffmpeg 子进程） | **选用** |
| Go | 性能与内存占用最优，部署简单 | 与前端不共用类型；AI SDK 生态较薄 | 不选；若将来 `audio-worker` 成为瓶颈可单独重写 |
| Python | AI / 评测生态最强 | 类型约束弱、并发模型复杂；三个 Web 子系统就要两门语言 | 不选 |
| Kotlin / Java | 生态成熟，可与未来 Android 共享 | 启动慢、内存大；小团队负担重 | 不选 |

| 框架 | 结论 | 理由 |
| --- | --- | --- |
| **Fastify 5** | 选用 | 插件与封装上下文清晰；结合 `fastify-type-provider-zod` 做请求校验与响应序列化；WebSocket、限流、CORS 等插件齐全 |
| NestJS | 不选 | 装饰器与 DI 层次多，样板代码重，小团队收益低 |
| Hono | 备选 | 轻量、多运行时；但本项目只跑 Node 容器，Fastify 生态更成熟 |

## 9. 后端：编排流水线、模型网关与 TTS 管线

流水线的设计目标是在 1.5 s 内放出第一句，并保证任何一句进入 TTS 的文本都能追溯到原文或受控模板。做法是“主帖快轨不等 LLM”加“按播放进度滚动合成”。

### 9.1 任务状态机

| 状态 | 进入条件 | 下一状态 |
| --- | --- | --- |
| `created` | `POST /jobs` 通过校验与幂等检查 | `admitted` / `rejected` |
| `admitted` | 配额 > 0、`R_daily` 未超、签名与 Attest 通过 | `planning` |
| `planning` | 快轨启动；语种判定与分支选择 | `scripting` |
| `scripting` | 分支 A 或 B 产出脚本，完成溯源与机审 | `synthesizing` |
| `synthesizing` | 按窗口滚动合成切片 | `completed` / `quota_exhausted` |
| 终态 | `completed`、`rejected`、`failed`、`cancelled`、`quota_exhausted` | — |

`degraded` 不是状态而是标记（备用 TTS、译文被丢弃、机审拦截等），随 `job.degraded` 事件下发。

### 9.2 流水线步骤

1. **快轨**：主帖正文按句切分（Node 内置 `Intl.Segmenter`，单片 ≤ 200 字符）；开场使用配置中的固定句式（按音色预生成并缓存）；第一句经出声前安全检查（两区，策略按区）后立即送 TTS。快轨不调用 LLM。
2. **语种判定**：站点 `langHint` + 轻量语种识别库；只有置信度低时才调用 LLM。对照 `target_lang` 与 `passthrough_langs` 决定分支；Tier 3 源语种强制走分支 B（PRD 5）。
3. **分支 A（同语种）**：一次结构化输出调用，返回 `order: unitId[]`、`emotions: Record<unitId, Emotion>`、`transitions: { afterUnitId, templateId, slots }[]`。串场词只能从配置里的句式模板选择，槽位只能引用从原文抽取的实体 ID，溯源因此是结构上保证的。输出校验：ID 全部存在、无重复、条数在 `[N_min, N_max]` / `N_brief` / `N_deep` 范围内、情绪属于 8 个枚举值。校验失败重试 1 次，再失败则按热度排序降级。
4. **分支 B（跨语种）**：先在源语种上做与 A 相同的选择；入选单元并发（`p-limit` 4）送 `VerbatimTranslator`（低温度、单条独立请求）；再由另一厂商或型号的校验模型输出 `{ entitiesKept, numbersKept, polarityKept, injectedContact }`。任一项不通过则用更严格的提示重译 1 次，仍不通过则丢弃该条并标记 `degraded`。
5. **安全层**：国内区所有待播文本（原文、译文、串场词）送机审；TTS 输入规范化：转义 SSML 保留字符、折叠超长重复标点和字符、单句最大时长与静音上限（PRD 6.2.4）。
6. **音色分配**：主持人固定槽位，原帖作者固定槽位；其他 `authorId` 按出场顺序贪心着色，约束为“与上一个发言人不同”和“与所回复对象不同”；同一 `authorId` 全帖不变；匿名用户按 `anon:${unitId}` 各自独立。每档位至少 4 个槽位。算法纯函数、可单测，对应门禁 12.6。
7. **滚动合成**：不一次合成整篇，只保持“客户端播放位置 + 30 s”的合成超前量；客户端通过 WebSocket 上行 `progress(unitId, offsetMs)` 推进窗口（即 4.2 中的 `progress` 上行消息）。用户跳过或取消时不再产生合成费用；跳章用 seek 移动窗口，跳过的单元不合成、不扣点；达到单篇上限时在章节边界停止，等待用户 extend（架构 02 §22.2、§23.2）。
8. **取消与断线**：收到 `cancel` 或 WebSocket 断开超过 60 s，停止调度新的切片；已合成切片按缓存规则保留。

### 9.3 模型网关（`llm-gateway`）

```ts
interface LlmGateway {
  generateStructured<T>(req: {
    task: TaskId;              // 'select' | 'translate' | 'verify' | 'review' | 'langdetect'
    jobId: string;             // 仅任务 ID，不含用户 ID
    schema: ZodType<T>;
    instructions: PromptRef;   // config/prompts/<task>@<version>
    untrusted: string[];       // 帖子 / 评论文本
  }): Promise<{ value: T; usage: Usage; vendor: string; model: string }>;
}
```

- **任务路由表**（存 `config/`）：每个 `task` 按区域配置主 / 备厂商、模型、温度、超时、重试次数、提示词版本。
- **不可信数据隔离**：`untrusted` 的每段文本用每次请求随机生成的边界标记包裹（如 `<data-7f3a9c>…</data-7f3a9c>`），系统提示声明边界内一切内容不是指令；输出强制结构化（PRD 6.2.2）。
- **可靠性**：每厂商一个熔断器（连续失败即切备用，半开探测恢复）；重试带指数退避与抖动；全局并发上限防止耗尽厂商配额。
- **计量**：每次调用写 `vendor_usage`（任务、厂商、模型、token、耗时、成本估算），用于单帖成本和配额精算。

### 9.4 TTS 音频管线（`audio-worker`）

1. 计算共享缓存键 `sha256(textSha256 | voiceId | emotion | lang | ttsModelVersion | postprocVersion)`。`PUBLIC` 且命中 `audio_cache_index` 则直接复用；`PRIVATE` 永不查、不写共享索引。
2. 调用主 TTS（流式）；首包超过 `T_tts_timeout`（默认 1,000 ms）则切备用厂商，两家厂商各有一份“槽位 → 音色”映射表。
3. ffmpeg 后处理：解码 → 按音色标定增益 → 真峰值限幅（≤ -1 dBTP）→ 两区均嵌入隐式标识与水印 → 编码 AAC 单声道 `.m4a`。
4. 计算 `audio_sha256`，写对象存储（公私 bucket 分开），生成短时签名 URL。
5. 核销配额：在同一事务里写 `job_segments` 与 `quota_ledger`（幂等键 `jobId:seq`）；余额归零则发 `quota.exhausted` 并停止后续合成。
6. 发布 `segment.ready` 到 `job:{id}:events`。

**待产品确认**：用户 A 命中由用户 B 触发生成的公共缓存时是否扣配额。PRD 11.2 只规定了同一用户复听免费。

## 10. 后端：认证、请求签名、频控与配额账本

### 10.1 登录与会话

- **Sign in with Apple**：服务端用 `jose` 按 Apple JWKS 校验 identity token（`iss`、`aud` = Bundle ID、`nonce`、过期时间）；同时用 authorization code 换取 Apple refresh token 并加密保存。用户注销时调用 Apple 的令牌吊销接口，这是支持 Sign in with Apple 的 App 在删除账户时的审核要求。
- **邮箱验证码**：6 位数字，Redis 只存 HMAC 哈希（`otp:{emailHash}`，TTL 10 分钟），最多尝试 5 次；重发冷却 120 s（`otp:cd:{emailHash}`）；按 IP 与设备再限流。
- **令牌**：访问令牌为 ES256 JWT，有效期 15 分钟，含 `sub`、`sid`、`region`、`tier`；刷新令牌为 256 位随机串，库中只存哈希，每次刷新轮换；旧刷新令牌被重用即吊销整个会话族。签名密钥放在云密钥服务，按季度轮换并保留旧公钥验签。
- **区域校验**：令牌里的 `region` 与当前部署区不一致时返回 `REGION_MISMATCH`。

### 10.2 设备证明（AttestProvider；iOS 为 App Attest）

1. 首次登录：`POST /attest/challenge` → 客户端 `DCAppAttestService.attestKey` → `POST /attest/verify`，服务端校验证书链、App ID 与计数器，把公钥存入 `devices`。
2. 之后的会话签发和每次 `POST /jobs` 都要求一个 assertion（本地签名，成本低），服务端校验并更新计数器。
3. 模拟器与不支持的设备只在开发环境放行；生产环境校验失败的设备进入风控名单，在后台可见。

### 10.3 请求签名与防重放（PRD 9.2.2）

登录成功时服务端下发 32 字节会话密钥 `k_sess`（仅经 TLS 传输，客户端存 Keychain）。所有写请求带三个头：`X-Ts`、`X-Nonce`、`X-Sig`。

```text
string_to_sign = METHOD \n PATH \n CANONICAL_QUERY \n X-Ts \n X-Nonce \n hex(SHA256(body))
X-Sig          = base64url(HMAC-SHA256(k_sess, string_to_sign))
```

服务端校验：时间窗 ±300 s；`SET nonce:{sid}:{nonce} NX EX 600` 失败即判重放；用常数时间比较签名。WebSocket 在 `hello` 时做一次同样的签名校验。

### 10.4 频控

| 规则 | 实现 | 超限返回 |
| --- | --- | --- |
| `R_daily`：每账号每日任务创建与重生成次数 | `INCR rl:daily:{userId}:{yyyymmdd}` + 当日到期 TTL | `DAILY_LIMIT` |
| 短窗口突发（按用户、按 IP、按设备） | Redis Lua 令牌桶 | 429 |
| 登录与验证码 | 按邮箱哈希与 IP 的滑动窗口 | 429 |
| 外部厂商并发 | 每厂商全局并发信号量（Redis） | 排队或切备用 |

### 10.5 配额账本

- **两层计量（统一额度池，主 PRD 11.2）**：底层 `vendor_usage` / `vendor_usage_items` 按各厂商实际计价口径记录每次调用的渠道（区域 × 厂商 × 模型 × 线路）、原始用量（输入 / 输出 Token、万字符、语音 Token、音频秒）与渠道成本（`vendors/pricing/<region>.yaml`）；用户侧 `quota_balances`（每用户每账期一行：`granted_mc`、`used_mc`、`rate_version`）与只追加的 `quota_ledger`（`delta_mc`、`reason` = grant / debit / refund / compensation、`usage_id`、`rate_version`）。点数以毫点整数存储，系数取 `credit-rates/<region>.yaml`。
- **核销**：每次模型调用（文本生成、翻译、语音合成、神经语音合成）完成后调用 `billing.settleCall`，在一个事务里写原始用量与成本、按「原始用量 × 费率系数 `K[r,ch,u]`」折算点数、写流水并 `UPDATE quota_balances SET used_mc = used_mc + mc`；`vendor_usage.idempotency_key` 唯一约束保证重复上报只核销一次，余额行锁串行化同一账户。容错切换时取「备用渠道折算」与「主渠道等价折算」的较低值。发起前只检查“余额 > 0”，结算后余额可为负，以实现“播完当前语句再停”的软着陆；负值本期保留、下期不追扣（PRD 11.2、U18）。每日 `billing-reconcile` 校验余额与成本两项对账。
- **账期**：`T_quota_reset` 未决前按自然月（归属区时区每月 1 日 0 点，主 PRD 13 U2）。表结构按“账期”设计，既支持订阅账期（由 App Store 的 `expiresDate` 推算），也支持自然月，由配置决定。
- **免扣**：预置样帖、提示音、经服务端确认故障后的本机朗读不产生扣减记录，机审与安全检查只记底层原始用量与成本、不折算点数；不存在客户端可调用的“免扣”接口。

### 10.6 订阅同步

- 购买时传入 `appAccountToken` = 用户 UUID，把 Apple 交易与账户关联。
- `POST /subscriptions/sync` 与 App Store Server Notifications V2 都用 Apple 官方库验证 JWS；按 `notificationUUID` 去重写入 `store_events`；处理 订阅、续订、升降级、过期、宽限期、退款；重算 `tier` 与 `granted_mc`。
- **架构风险**：一个 App 在 App Store Connect 中只能配置一个生产环境通知地址，而本产品有两个互不相通的区域。可选方案：① 国内版与海外版使用两个独立 Bundle ID，各自配通知地址，合规边界最清楚，也符合 PRD 9.3 “按发行区域包体绑定”的写法；② 单个 App + 一个无状态路由入口，按 `appAccountToken` 里编码的区域位转发，但交易数据会跨境经过路由，需要合规评估。推荐 ①。这也影响第 2.3 节的区域路由：采用 ① 时区域由安装的包决定。

## 11. 数据库设计（PostgreSQL 18）

每个区域一个托管 PostgreSQL 实例（主备高可用、同区跨可用区），不做跨区复制。主键一律用应用生成的 UUIDv7（按时间有序，索引友好）。个人内容字段做应用层加密，每个用户一把数据密钥，删除密钥即可让该用户在备份中的数据也无法读取。

### 11.1 表清单

### 11.2 关键 DDL（配额）

```sql
-- 底层：原始用量与渠道成本（按厂商实际计价口径，不换算）
CREATE TABLE vendor_usage (
  id              uuid        NOT NULL,
  idempotency_key text        NOT NULL,            -- usage:{jobId}:{stage}:{seq}
  job_id          uuid,
  stage           text        NOT NULL,            -- select / translate / tts / cache_hit / moderation ...
  seq             int         NOT NULL,
  channel         text        NOT NULL,            -- 区域.厂商.模型.线路
  failover_from   text,
  price_version   text        NOT NULL,
  cost_micros     bigint      NOT NULL,            -- 本区币种微单位
  billable        boolean     NOT NULL,
  created_at      timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (id, created_at),
  UNIQUE (idempotency_key, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE vendor_usage_items (
  usage_id uuid    NOT NULL,
  unit     text    NOT NULL CHECK (unit IN ('in_tokens','out_tokens','cached_in_tokens','chars_10k','speech_tokens','audio_s')),
  qty      numeric NOT NULL,
  PRIMARY KEY (usage_id, unit)
);

-- 用户侧：统一额度池（毫点，1 点 = 1000 毫点）
CREATE TABLE quota_balances (
  user_id      uuid        NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  period_start timestamptz NOT NULL,
  period_end   timestamptz NOT NULL,
  granted_mc   bigint      NOT NULL,
  used_mc      bigint      NOT NULL DEFAULT 0,      -- 可大于 granted_mc（负余额，下期不追扣）
  rate_version text        NOT NULL,                -- 账期开始时固定的费率系数版本
  PRIMARY KEY (user_id, period_start)
);

CREATE TABLE quota_ledger (
  id              uuid        NOT NULL,
  user_id         uuid        NOT NULL,
  period_start    timestamptz NOT NULL,
  delta_mc        bigint      NOT NULL,            -- 扣减为负，发放 / 退还 / 补偿为正
  reason          text        NOT NULL CHECK (reason IN ('grant','debit','refund','compensation')),
  usage_id        uuid,                            -- 扣减与退还关联到底层一次调用
  rate_version    text,
  idempotency_key text        NOT NULL,
  created_at      timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (id, created_at),
  UNIQUE (idempotency_key, created_at)
) PARTITION BY RANGE (created_at);
```

分区表上的唯一约束必须包含分区键，所以幂等性的最终保障放在 Redis（`SET idem:{key} NX EX 86400`）+ 当月分区内唯一约束两层。分区由 `pg_partman` 或定时任务按月预建。

### 11.3 应用层加密与删除

- 每用户一把 256 位数据密钥（DEK），由区域 KMS 主密钥包裹后存入 `user_keys`；`email_enc`、`clean_text_enc`、`translated_enc` 用 AES-256-GCM 加密。
- 注销工单顺序：吊销 Apple 令牌 → 删除 `user_keys` 行 → 级联删除各表 → 删除对象存储 `private/{userId}/` 前缀 → 写仅含哈希的完成记录。删密钥一步完成后，备份中的该用户密文也无法还原，满足海外 24 小时擦除要求（PRD 9.3）。

### 11.4 连接、权限、迁移与备份

- **连接池**：每进程用 postgres.js 小连接池；实例多时前置数据库代理（AWS RDS Proxy、阿里云 RDS 数据库代理）。
- **数据库角色**：`app_rw`（三个业务进程）、`admin_limited`（按列授权，读不到 `*_enc` 列与 `user_keys`）、`migrator`（只在部署流水线使用）。
- **迁移**：`drizzle-kit generate` 生成 SQL，人工评审后入库；部署时先跑迁移再滚动发布；破坏性变更采用“先扩后缩”（expand / contract），确保新旧代码都能跑。
- **备份**：托管自动备份 + 7 天时间点恢复（PITR）；备份留在本区；每季度做一次恢复演练。

## 12. 缓存、队列与对象存储

Redis 在本系统里不是“可丢的缓存”，而是承载限流、防重放、进程间消息和队列的协调层，因此配置为 `maxmemory-policy noeviction`（BullMQ 的要求），并开启持久化与主备。音频本体只放对象存储，客户端通过签名 URL 直接下载，不经过应用服务器。

### 12.1 Redis 键设计

| 键 | 类型 | TTL | 用途 |
| --- | --- | --- | --- |
| `nonce:{sid}:{nonce}` | String | 600 s | 请求防重放 |
| `sess:revoked:{sid}` | String | 访问令牌剩余有效期 | 会话吊销黑名单 |
| `otp:{emailHash}` · `otp:cd:{emailHash}` | Hash · String | 600 s · 120 s | 验证码哈希与重发冷却 |
| `rl:daily:{userId}:{yyyymmdd}` | String（计数） | 当日结束 + 1 h | `R_daily` |
| `rl:tb:{scope}:{id}` | Hash（令牌桶） | 120 s | 短窗口限流（Lua 脚本原子执行） |
| `idem:{key}` | String | 24 h | `POST /jobs` 幂等、配额核销幂等 |
| `job:{id}:state` | Hash | 1 h | 任务实时状态、滚动合成窗口位置 |
| `job:{id}:events` | Stream（`MAXLEN ~2000`） | 1 h | WebSocket 转发与断线补发 |
| `jobs:dispatch` · `tts:requests` · `tts:requests:fast` | Stream + 消费组 | — | 进程间任务分发 |
| `vendor:sem:{vendor}` | Sorted Set | — | 厂商全局并发信号量 |
| `cb:{vendor}` | Hash | 60 s | 熔断器状态 |
| `config:active:{kind}` | String | 5 min | 当前生效配置包的本地缓存 |
| `bull:*` | BullMQ 内部 | — | 异步任务队列 |

键里不出现明文邮箱、正文、URL。国内区使用阿里云 Redis 开源版 7.0（社区版协议，D6 已定），代码只用 Redis 7.0 社区版命令集，不再「验证后再换」。

### 12.2 BullMQ 异步队列

| 队列 | 触发 | 内容 | 重试 / 告警 |
| --- | --- | --- | --- |
| `deletion` | `DELETE /account` | 按 11.3 的顺序执行注销工单 | 指数退避；距离 24 h 期限不足 4 h 仍未完成即告警 |
| `private-sweeper` | 每分钟定时 | 删除已确认播放或超过 `T_priv_ttl` 的私有切片 | 积压超过 5 分钟即告警 |
| `cache-gc` | 每日 | 清理 90 天未命中的公共缓存与索引 | — |
| `quota-period` | 每小时 | 滚动到期账期、发放新账期配额 | 失败即告警 |
| `store-reconcile` | 每日 | 用 App Store Server API 对账订阅状态，补漏接的通知 | — |
| `partition-maint` | 每月 | 预建下月分区、删除过期分区 | — |
| `job-text-purge` | 每小时 | 置空完成超过 24 h 的 `job_units` 正文字段 | — |

队列执行器挂在 `orchestrator` 进程内，定时任务用 BullMQ 的 repeatable job，多实例下不会重复触发。

### 12.3 限流算法

令牌桶用一段 Lua 脚本实现：读取 `tokens` 与 `ts`，按流速补充，取一个，写回并刷新 TTL，整个过程在 Redis 内原子完成。各维度参数（容量、流速）放在配置包里，可以不发版调整。`R_daily` 用简单计数即可，不需要滑动窗口。

### 12.4 对象存储布局

| Bucket（每区一套） | 对象键 | 访问方式 | 生命周期 |
| --- | --- | --- | --- |
| `audio-public` | `pub/{cacheKey[0:2]}/{cacheKey}.m4a` | 私有 bucket + 签名 URL（TTL 10 min）；可加 CDN（URL 鉴权） | 由 `cache-gc` 管理，生命周期规则 180 天兜底 |
| `audio-private` | `priv/{userId}/{jobId}/{seq}.m4a` | 服务端加密（KMS）+ 签名 URL，TTL = min(`T_priv_ttl`, 10 min)；不过 CDN | `private-sweeper` 主动删除，生命周期规则 1 天兜底 |
| `samples` | `samples/{sampleId}/{lang}.m4a` | CDN 公开读 | 永久 |
| `config-bundles` | `{kind}/{version}.json` + `.sig` | 客户端经 `GET /config/bundle` 读取 | 永久 |
| `admin-web` · `testbench-web` | SPA 静态文件 | 只在零信任网关后可达 | 随发布 |

国内区用阿里云 OSS，海外区用 Cloudflare R2（S3 兼容 API、无出口流量费，D18 已定）。应用代码只依赖 S3 兼容接口写入；海外读取经边缘层 Cloudflare Workers + Hono 分发（Ed25519 签名 URL 校验、公共切片边缘缓存、下架时调用缓存清除接口），国内经 OSS + CDN；签名格式两区相同，共用 `packages/signed-url`（D17、D18）。

## 13. 托管、容器化与基础设施

所有后端进程以容器运行在托管的 Serverless 容器平台上（国内阿里云 SAE，海外 AWS ECS Fargate），不自建 Kubernetes。两个区域的资源用同一套 Pulumi 代码创建，差异只在 Provider 与配置。

### 13.1 容器镜像

同一个 Dockerfile 产出两个镜像：`server`（bff / orchestrator / admin-api）和 `server-audio`（额外带 ffmpeg，用于 audio-worker），避免所有进程都背上 ffmpeg 的体积与漏洞面。

```dockerfile
# syntax=docker/dockerfile:1
FROM node:26-bookworm-slim@sha256:<pinned> AS base
RUN corepack enable
WORKDIR /repo

FROM base AS build
COPY pnpm-lock.yaml pnpm-workspace.yaml ./
RUN pnpm fetch
COPY . .
RUN pnpm install --frozen-lockfile --offline \
 && pnpm turbo run build --filter=server... \
 && pnpm deploy --filter=server --prod /out

FROM node:26-bookworm-slim@sha256:<pinned> AS server
RUN apt-get update && apt-get install -y --no-install-recommends tini && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY --from=build /out ./
USER node
ENTRYPOINT ["tini", "--", "node"]
CMD ["dist/entry/bff.js"]

FROM server AS server-audio
USER root
RUN apt-get update && apt-get install -y --no-install-recommends ffmpeg && rm -rf /var/lib/apt/lists/*
USER node
CMD ["dist/entry/audio-worker.js"]
```

- 非 root 运行、只读根文件系统、`tini` 作为 PID 1 转发信号；基础镜像按摘要固定，Renovate 自动提升级 PR。
- CI 对镜像做漏洞扫描（Trivy）并生成 SBOM；镜像推送到各区的 ACR / ECR，两个区拉取同一摘要。
- **优雅停机**：收到 SIGTERM 后停止接新连接，向 WebSocket 客户端发 `reconnect` 提示，当前切片合成完再退出（上限 30 s）；未确认的 Stream 消息由其他实例 `XAUTOCLAIM` 接管。

### 13.3 网络拓扑（每区）

- 一个 VPC，三层子网：公网子网（ALB、NAT）、应用子网（容器）、数据子网（RDS、Redis），至少跨两个可用区。
- 安全组最小化：ALB → `bff` 端口；应用子网 → RDS 5432、Redis 6379；其他一律拒绝。`orchestrator` 与 `audio-worker` 不挂任何入站规则。
- 出站只经 NAT；对象存储走 VPC 内网端点，不经公网。

### 13.4 环境矩阵

| 环境 | 用途 | 数据 | 规模 |
| --- | --- | --- | --- |
| `local` | 开发者本机：Docker Compose（PostgreSQL 18、Valkey、S3 兼容本地存储 SeaweedFS、Mailpit）+ 供应商 Mock 服务 | 合成数据 | 单机 |
| `cn-staging` · `intl-staging` | 预发：测试台架、门禁、TestFlight 包 | 合成 / 公开样本 | 与生产同拓扑、最小规格 |
| `cn-prod` · `intl-prod` | 生产 | 真实用户 | 每种进程 ≥ 2 实例，跨可用区 |

供应商 Mock 服务支持“录制 / 回放”：第一次调用真实厂商并把响应存成 fixture，之后只回放，本地开发和 CI 不产生模型费用。

### 13.5 Pulumi

- 一个 Pulumi 项目、四个 stack（`cn-staging`、`cn-prod`、`intl-staging`、`intl-prod`）；组件封装为 `RegionStack`，内部按 Provider 选择阿里云或 AWS 资源。
- 状态存储使用自管后端：国内 stack 存 OSS，海外 stack 存 S3，避免资源元数据跨境。密钥类配置用各区 KMS 加密。
- 变更流程：PR 上跑 `pulumi preview` 并把差异贴到 PR；合并后先对 staging 执行 `pulumi up`，生产需要人工审批。

### 13.6 弹性伸缩

| 进程 | 最小 / 最大实例（生产初始） | 扩容依据 |
| --- | --- | --- |
| `bff` | 2 / 20 | CPU 60%、WebSocket 连接数 |
| `orchestrator` | 2 / 20 | `jobs:dispatch` 积压与在途任务数 |
| `audio-worker` | 2 / 40 | `tts:requests` / `tts:requests:fast` 积压、CPU |
| `admin-api` | 1 / 2 | 固定 |

Fargate 用 CloudWatch 自定义指标（Stream 积压）做目标跟踪；SAE 以 CPU / 内存和定时策略为主，是否支持按自定义指标伸缩需在接入时确认。容量基线按 PRD 10.2（100 QPS 起、可扩到 2,000 QPS）用 k6 压测校准。

## 14. 可观测性与运维

统一用 OpenTelemetry 采集日志、指标、链路，导出到各区自己的后端（国内 SLS / ARMS，海外 CloudWatch / X-Ray）；任何可观测数据都不出区，也不含帖子正文。

### 14.1 日志

- pino 输出 JSON；`redact` 固定屏蔽 `body`、`text`、`cleanText`、`url`、`cookie`、`authorization`、`email` 等路径；在 CI 里用一个测试确认带敏感字段的对象打印后不含原文。
- 每条日志带 `trace_id`、`task_id`、`region`、`role`；不带 `user_id`（需要关联时在数据库里由 `task_id` 反查）。
- 保留：业务日志 30 天；国内生成安全审计日志单独 SLS Project，≥ 180 天，只有合规角色可读（PRD 9.3）。

### 14.2 指标

| 类别 | 指标 | 用途 |
| --- | --- | --- |
| 接口 | 每路由请求数、错误率、延迟分位（RED） | 基础健康 |
| 体验 | 服务端 TTFA（任务受理 → 第一个 `segment.ready`）直方图，按分支拆分；客户端上报的端到端 TTFA 与卡顿率 | PRD 10.1 |
| 管线 | Stream 积压、在途任务、滚动窗口滞后 | 伸缩与容量 |
| 供应商 | 每厂商首包延迟、错误率、熔断次数、备用切换率 | 降级与商务 |
| 质量 | 译文校验失败率、单元被丢弃率、机审拦截率、客户端摘要不一致次数 | 防篡改与合规 |
| 成本 | 每分钟合成音频成本、每帖 token、公共缓存命中率 `η_pub` | 精算与 PRD 1.3 |
| 合规 | 注销工单积压与最长等待、私有切片最长存活时间 | PRD 9.1.3、9.3 |
| 商业 | 配额核销量、拦截层展示与转化 | PRD 11.3 |

### 14.3 链路追踪

`bff` 入口创建 trace；写入 Redis Stream 的消息携带 W3C `traceparent` 字段，`orchestrator` 与 `audio-worker` 续接；对 LLM、TTS、机审、对象存储的调用各是一个 span，属性只记厂商、模型、字节数、耗时。测试台架的时延时间线直接读取这些 span。

### 14.4 SLO 与告警

| SLO | 目标 | 告警 |
| --- | --- | --- |
| 音频不断流可用性 | ≥ 99.9%（28 天滚动） | 错误预算 1 小时燃烧率 > 14 即告警 |
| 同语种冷启动 TTFA | P95 ≤ 1.5 s | 连续 15 分钟超标 |
| 跨语种冷启动 TTFA | P95 ≤ 2.8 s | 连续 15 分钟超标 |
| 缓存直读 TTFA | P95 ≤ 300 ms | 连续 15 分钟超标 |
| 客户端摘要不一致 | 0 | 出现 1 次即告警 |
| 海外注销 24 h 内完成 | 100% | 任一工单超过 20 h 未完成 |

告警分两级：紧急级推送到手机（云监控短信 / 电话、或 Sentry 与 IM 机器人），其余汇总成每日摘要。小团队的原则是：只有“需要立刻动手”的事件才能半夜叫醒人。

### 14.5 拨测与运维手册

- **拨测**：每区每 5 分钟用专用测试账号提交一篇固定公开样帖，完整走一遍任务并记录 TTFA；测试账号有独立配额、不计入业务指标。
- **运维手册**（`docs/runbooks/`）：厂商故障与手动切换、配额异常与批量补偿、摘要不一致排查、注销积压处理、数据库主备切换与时间点恢复、证书固定公钥轮换、KMS 与签名密钥轮换、配置包回滚。
- **证书固定轮换是最危险的操作**：App 里必须始终同时固定当前公钥和至少一个备用公钥；轮换顺序为“发布含新公钥的 App → 等大部分用户升级 → 服务端换证书”，顺序错了会让老版本客户端全部断连。

## 15. 安全架构

安全设计围绕 PRD 9 的两条主线：保护本 App 用户自己的身份、凭证、收听行为和私有内容；保证播出的原文不被篡改。第三方平台的反爬与原帖内容脱敏不在范围内（PRD 1.1）。

### 15.1 威胁模型

| 威胁 | 攻击面 | 控制措施 | PRD |
| --- | --- | --- | --- |
| 站点凭证泄露 | 设备备份、日志、崩溃报告、App Group | Keychain `ThisDeviceOnly`；WebKit 非持久存储；日志与崩溃报告脱敏；App Group 只放 URL | 9.1.1 |
| 中间人窃听 / 篡改 | 公共 Wi-Fi、恶意代理 | TLS 1.3 + 公钥固定（含备用公钥）；切片摘要校验 | 9.2.1、9.2.3 |
| 请求伪造与重放 | 抦包重发、脚本盗刷 | 会话级 HMAC 签名、nonce、时间窗；App Attest；频控 | 9.2.2、11.2.3 |
| 伪造免扣状态 | 客户端上报“离线 / 故障” | 不存在客户端免扣接口，免扣只由服务端状态决定 | 11.2.2 |
| 间接提示词注入 | 帖子 / 评论里的指令、假联系方式 | 随机边界、结构化输出、受控句式模板 + 实体溯源、独立译文校验、分支 A 不输出正文 | 6.2 |
| SSML / 音频滥用 | 控制标签、超长重复字符 | TTS 边界转义与折叠、单句时长与静音上限 | 6.2.4 |
| SSRF | 恶意链接指向内网 | 客户端 URL 守卫（含重定向和 DNS 解析后校验）；服务端不代抓任何用户 URL | 7.1 |
| 私有音频跨用户泄露 | 共享缓存键碰撞、侧信道探测 | PRIVATE 不查不写共享索引；按用户前缀存储、KMS 加密、短时签名 URL；公共缓存只接受白名单站点 | 9.1.3 |
| 供应商留存用户数据 | 外部 LLM / TTS | ZDR 合同；请求只带任务 ID；禁用批处理等不支持 ZDR 的接口 | 9.1.2 |
| 后台越权 | 后台账号被盗、内部人员误用 | Passkey + 零信任网关、RBAC、数据库列级授权、只追加审计 | 9.3 |
| 供应链攻击 | 恶意依赖、被接管的包 | 锁文件、Renovate + 人工评审、镜像扫描与 SBOM、最少依赖原则 | — |
| 物理肩窥 | 锁屏与车机屏幕 | 锁屏隐私模式只展示通用标题 | 9.1.4 |

### 15.2 加密一览

| 位置 | 方式 | 密钥归属 |
| --- | --- | --- |
| 传输 | TLS 1.3；App 端公钥固定 | 证书由云证书服务管理 |
| 手机数据库 | SQLCipher AES-256 | Keychain 中的随机密钥 |
| 手机音频缓存 | AES-GCM（CryptoKit） | Keychain |
| 服务端个人字段 | AES-256-GCM，每用户一把 DEK | 区域 KMS 包裹 |
| 数据库 / Redis / 对象存储静态 | 云厂商静态加密；私有 bucket 用 KMS 密钥 | 区域 KMS |
| 配置包 | Ed25519 签名（防篡改，不加密） | 签名私钥只在 CI 的受保护环境中使用 |

### 15.3 密钥与凭据清单

JWT 签名密钥、配置包签名密钥、KMS 主密钥、供应商 API 密钥、App Store Server API 密钥、Sign in with Apple 密钥、数据库各角色密码、Sentry DSN。全部存在各区的凭据服务中，容器启动时注入；代码仓库、CI 日志、AI 代理的上下文里不出现任何生产密钥。轮换周期：JWT 签名密钥每季度，供应商密钥每半年或泄露即轮换。

### 15.4 权限最小化

- 每种进程一个独立的云角色（RAM 角色 / IAM Role）：`audio-worker` 可写两个音频 bucket；`bff` 只能生成签名 URL；`admin-api` 只读配置 bucket 与样帖 bucket。
- CI 通过 OIDC 联合身份拿临时凭证部署，不保存长期云密钥；生产部署需要人工审批。
- 生产数据库不对公网开放；人工排障经堡垒机或会话管理服务进入，并记入审计。

### 15.5 安全开发流程

- 每个 PR：类型检查、Lint、单测、依赖漏洞扫描、密钥泄露扫描（gitleaks）。
- **供应链**：pnpm 只允许白名单依赖运行安装脚本，新版本发布满 3 天才安装；GitHub Actions 按 commit SHA 固定、镜像按 digest 固定；云凭据只走 OIDC；CI 检查许可证白名单。完整规范见 `05-toolchain-and-resources.md` §2.5。
- 每次发版：镜像扫描与 SBOM、PRD 12.3 / 12.4 的安全门禁（注入拦截、凭证落盘、缓存隔离、身份字段泄露）。
- 上线前做一次外部渗透测试，覆盖 API、WebSocket、iOS 包体逆向与本地存储。

## 16. AI 与语音集成

所有模型与语音调用都经过 `llm-gateway` 和 `tts` 模块（见第 9 节），业务代码不直接引用任何厂商 SDK。厂商、模型、提示词、schema、音色全部是配置，经评测门禁后发布。

### 16.1 分区供应商矩阵

| 任务 | 国内区（主 / 备） | 海外区（主 / 备） | 要求 |
| --- | --- | --- | --- |
| 评论选拔、排序、串场模板选择 | 豆包（火山方舟）/ 通义千问（百炼） | Claude（Anthropic API ZDR 或 Bedrock）/ Gemini（Vertex AI） | 结构化输出、长上下文（单帖评论可达数万字） |

| 译文校验 | 与翻译不同的厂商或型号 | 同 | 输出布尔判定 + 证据字段 |

| 主轨 TTS | 豆包语音合成 2.0 / 阿里云 CosyVoice | ElevenLabs / Google Cloud TTS 或 Azure Speech | 流式、多音色、情绪可控（Tier 1） |
| 出声前审核 | 阿里云内容安全 / 火山引擎内容安全 | OpenAI Moderation / LLM 分类器 | 国内覆盖全部待播文本 |

国内只能使用已完成生成式 AI 备案的模型；通过 API 调用已备案模型的应用还要到地方网信办登记，并在显著位置公示模型名称与备案号（[央视网](https://m.gmw.cn/2026-07/10/content_1304528476.htm)）。App 设置页的“模型与备案信息”由配置包下发。

### 16.2 零数据留存（海外）

| 厂商 | 现状 | 对本项目的影响 |
| --- | --- | --- |
| Anthropic | ZDR 需销售审核、按组织开通；结构化输出为“有条件支持”，JSON schema 会缓存至最后使用后 24 小时；批处理接口不支持 ZDR（[文档](https://platform.claude.com/docs/en/build-with-claude/api-and-data-retention)） | schema 里只放字段名与枚举，不放用户数据；禁用批处理；不使用需 30 天留存的模型 |
| Amazon Bedrock | 数据处理方是 AWS，留存条款看 AWS 一侧 | 后端本就在 AWS，合同路径最短，需书面确认 |

| ElevenLabs | 零留存模式只对部分企业客户开放，开启后官方无法协助排查（[文档](https://elevenlabs.io/docs/eleven-api/resources/zero-retention-mode/llms.txt)） | 拿不到就把备用 TTS 提升为主线路 |

### 16.3 提示词与 schema 管理

- 目录：`config/prompts/<task>/<version>.md`、`config/schemas/<task>/<version>.ts`（zod）；版本号不可变，修改即新版本。
- 每个版本在 `evals/` 下有对应的 promptfoo 用例；只有在两个区域的厂商组合上都通过门禁的版本才能进入配置包。
- 生产请求记录使用的 `task@version`、厂商、模型，便于问题回溯与灰度对比。

### 16.4 音色与情绪

- `config/voices/` 定义每个语种、每个订阅档位的音色槽位表：槽位 →（厂商、音色 ID、标定增益），主备厂商各一份。
- 8 个情绪枚举（PRD 8.2）在每家厂商上映射为各自的风格参数；Tier 2 语种只允许 `NEUTRAL` / `EMPHATIC` 等低幅度情绪；Tier 3 不配置音色（PRD 5）。
- 新音色上线前在测试台架做响度标定与自然度评测（PRD 12.6）。

### 16.5 成本控制

- 滚动合成窗口保证只为即将播放的内容付费；公共缓存复用已生成的公开内容。
- 选拔调用只发评论摘要信息与前 N 条候选（按热度预筛），控制输入 token；提示词固定前缀可以利用厂商的提示缓存。
- `vendor_usage` 汇总到“每分钟合成音频成本”，是 `Q_*` 与 `P_*` 精算的输入。

### 16.6 深度合成标识

- **显式**：预录的语音提示片段作为客户端内置资源，按配置插入播报开头；不走在线 TTS，不耗配额。仅音频提示是否满足《标识办法》仍待合规确认（PRD 9.3）。
- **隐式**：音频文件元数据写入生成方、内容编号与生成时间。
- **数字水印**：在限幅之后、编码之前嵌入；实现方案（厂商能力或开源方案如 AudioSeal）待评估，需在测试台架验证经过 AAC 编码后仍可检出。

## 17. 管理后台

管理后台是 React SPA + 独立 `admin-api` 的前后端分离结构，在两个区域各部署一套，只操作本区数据。权限在三层同时执行：零信任网关（谁能打开）、`admin-api` RBAC（能做什么）、数据库列级授权（能读到什么）。

### 17.4 配置发布流程

1. 在 Git 中修改 `config/`（提示词、schema、站点规则、音色、配额参数）并提 PR。
2. CI 在两个区域的预发环境跑对应门禁；通过后合并。
3. CI 打包并用 Ed25519 私钥签名，上传到两个区的 `config-bundles`，状态为“候选”。
4. `publisher` 在各区后台选择版本发布，可按用户哈希设置灰度比例；指标异常时一键回滚到上一版本。
5. 服务端在 5 分钟内拉取生效；客户端下次启动或回到前台时拉取，验签后生效。

### 17.5 安全要点

- `admin-api` 使用 `admin_limited` 数据库角色，对 `*_enc` 列、`user_keys`、正文字段没有 SELECT 权限；国内生成安全审计日志在独立 SLS Project，后台只有 `compliance` 角色能跳转查看。
- 所有写接口经过审计中间件，写入操作人、动作、对象、前后值（前后值中的个人信息先脱敏）。
- 为防 CSRF，Cookie 使用 `SameSite=Strict`，写请求另带自定义头；CSP 禁止内联脚本与第三方域。

## 18. 后端 Web 测试台架与质量体系

测试台架由两部分组成：`testbench-web`（React SPA）和 `testbench-runner`（Node 服务，只部署在两区预发环境）。runner 以库的形式引入后端的 `pipeline` 等模块，在每一步挂检查点采集中间产物；也可以作为模拟客户端走完整的 `bff` + WebSocket 链路。

## 19. CI/CD 与发布流程

采用主干开发（trunk-based）：短生命周期的功能分支 → PR → 必须全部检查通过 → squash 合并到 `main`。`main` 自动发布到两个预发环境；生产发布由人工审批触发。后端与基础设施用 GitHub Actions，iOS 用 Xcode Cloud。

### 19.1 流水线

| 工作流 | 触发 | 步骤 | 阻断条件 |
| --- | --- | --- | --- |
| `ci` | 每个 PR | 安装（Turborepo 缓存）→ Biome → typecheck → 单元 → 集成（Testcontainers）→ 黄金向量 → OpenAPI 一致性 → gitleaks → 镜像构建（不推送） | 任一失败 |
| `infra-preview` | 改动 `infra/` 的 PR | 对四个 stack 执行 `pulumi preview`，差异贴到 PR | 预览失败 |
| `evals` | 改动 `config/`、`evals/`、`pipeline`、`llm-gateway` 的 PR；每日定时 | 在两区预发环境跑 promptfoo 与门禁子集，报告贴到 PR | 任一门禁不达标 |
| `deploy-staging` | 合并到 `main` | 构建并推送镜像到 ACR / ECR（按摘要）→ `pulumi up`（staging）→ 运行迁移 → 滚动发布 → 冒烟测试 → 测试台架确定性门禁 | 冒烟或门禁失败则自动回滚 |
| `deploy-prod` | 手动触发 + GitHub Environment 审批 | 选择已在 staging 验证的镜像摘要 → 迁移（只允许扩展型）→ 分批发布 → 拨测与 SLO 观察 15 分钟 | 观察期内 SLO 爆红则自动回滚 |
| `config-release` | `config/` 合并后 | 打包 → Ed25519 签名 → 上传两区为“候选” | 签名或上传失败 |
| iOS（Xcode Cloud） | PR / `main` / 发版 tag | 测试 → TestFlight 内测 → App Store 提交 | 测试失败 |

CI 对云的访问都走 OIDC 临时凭证；GitHub 不保存长期云密钥。GitHub Actions 托管的 runner 在海外，向阿里云推送镜像与部署可能较慢；如果成为瓶颈，国内部署可改用阿里云云效 Flow 或国内自托管 runner。镜像与代码不含用户数据，不涉及数据出境。

### 19.2 数据库迁移

- 迁移以一次性任务执行（ECS RunTask / SAE Job），使用 `migrator` 角色，在应用滚动发布前完成。
- 一律“先扩后缩”：加列 / 加表 / 加索引（`CONCURRENTLY`）随代码发布；删列、改类型等收缩动作在旧代码完全下线后的下一个发布里做。这样任何时候回滚应用镜像都不需要回滚数据库。
- CI 检查迁移文件：禁止在同一个迁移里既扩又缩；大表加索引必须 `CONCURRENTLY`。

### 19.3 发布与回滚

- 镜像不可变、按摘要引用；部署记录 = Git SHA + 镜像摘要 + 配置包版本。
- ECS 使用滚动更新 + 部署熔断器（健康检查失败自动回滚）；SAE 使用分批发布与灰度。
- 回滚 = 重新部署上一个镜像摘要；配置问题优先在后台回滚配置包，不需要重新部署。
- 同一个镜像摘要先发一个区，观察 24 小时后再发另一个区，把两个区当作天然的分批。

### 19.4 特性开关

- 开关定义在配置包里，服务端与客户端共用；支持布尔开关、按用户哈希的百分比、按档位、按客户端版本。
- 必备的紧急开关：切换主备 LLM / TTS、关闭分支 B（只播同语种）、关闭公共缓存、关闭某个站点适配器、强制客户端升级。
- 不引入第三方开关服务，避免又多一个跨境的数据流。

## 20. Vibe coding 最佳实践（通用）

本项目大部分代码由 AI 编码代理产出。核心原则是：规则靠机器执行，不靠提示词嘱咐；代理负责写，类型系统、测试、CI 门禁和人工评审负责把关。

### 20.1 仓库上下文文件

- 根目录 `AGENTS.md`（并让 `CLAUDE.md` 引用它）控制在 200 行以内，只写代理每次都需要的信息：
  1. 一段话产品说明与目录地图（指向第 3 节结构）。
  2. 常用命令：`pnpm verify`（lint + typecheck + test 一次跑完）、`make ios-test`、`pnpm db:migrate:new`、`pnpm contracts:gen`。
  3. 红线（禁区）：不记录正文 / URL / Cookie；不把用户 ID 传给外部厂商；不弱化证书固定与签名校验；不在 App Group 存凭证；不引入第三方分析 SDK；帖子卡片不展示任何计数（PRD 7.3 引用的根 `AGENTS.md` 禁区）。
  4. 完成定义：测试先行、`pnpm verify` 通过、更新相关文档、PR 描述附测试证据。
- 每个 `apps/*` 下放自己的 `AGENTS.md`，写该端的分层规则、命名、示例文件路径。代理在哪个目录工作，就读到哪个目录的规则。
- “为什么这样做”写在 `docs/adr/`，`AGENTS.md` 只链接不复述。

### 20.2 规格先行、测试先行

1. 每个功能先写一份很短的任务规格（`docs/specs/<feature>.md`）：目标、接口变更、数据变更、验收标准（逐条对应 PRD 章节）。
2. 让代理先把验收标准写成失败的测试，人工确认测试表达的是对的需求，再让代理实现。
3. 涉及契约的改动，先改 `packages/contracts` 与 `canonical-spec`，生成产物与黄金向量先过 CI，再分别改两端。

### 20.3 任务拆分

- 一个 PR 只做一个垂直切片，差异尽量控制在 400 行以内（不含生成代码）。越大的差异，代理越容易引入不相关的改动，人也越难审。
- 复杂任务先让代理进入计划模式，输出涉及的文件、步骤和风险，确认后再动手。
- 同一个问题代理连续两次没做对，就停下来重新拆分或补充上下文，不要让它继续试错。

### 20.4 机器护栏

- TypeScript strict + `noUncheckedIndexedAccess`、Swift 6 strict concurrency：把大量“看起来能跑”的错误提前到编译期。
- 本地 git hook（lefthook）跑快速检查；CI 跑全量；`main` 分支保护，不允许跳过检查合并。
- 生成代码文件头标注 `DO NOT EDIT` 并在 Biome / SwiftLint 中排除；CI 校验生成产物与源一致，代理手改生成代码会被拦下。
- 架构约束写成可执行规则：包依赖方向（Turborepo、SPM 包声明）、禁止的导入（如 Features 层直接引用 GRDB）。

### 20.5 安全的代理环境

- 代理只拿到本地与预发环境的权限，永远没有生产凭证；仓库只有 `env.example`（无点前缀，避免被 `.env.*` 的拒绝规则连带挡住）。
- 厂商 Mock 服务让代理不需要真实密钥就能跑完整测试；需要真实厂商的评测只在 CI 里用受控密钥跑。
- MCP 工具按最小权限接入：Sentry（查问题）、GitHub（PR 与 Issue）、预发数据库只读账号。不给代理任何生产数据库或云控制台的写权限。

### 20.6 人工评审

- 以下路径的变更必须人工逐行审：`auth`、`quota`、`billing`、`deletion`、`platform/crypto`、`drizzle/`（迁移）、`canonical-spec`、`infra/`、iOS `Storage` 与 `Networking`、`config/prompts`。用 GitHub 的 CODEOWNERS 和分支规则强制。
- 审查重点：是否编造了不存在的 API（对照官方文档核实）、是否惄悄放宽了校验或捕获并吞掉了错误、是否超出任务范围修改了其他文件、是否留下了日志泄露。
- 可以再用一个独立的代理做第二遍评审（不要让写代码的同一个会话自己审自己）。

### 20.7 可复用的任务模板

把反复出现的任务做成仓库内的命令或技能文件，例如：`add-endpoint`（zod → 路由 → 测试 → OpenAPI → Swift 客户端）、`add-migration`、`add-site-adapter`（规则 + fixture + 测试）、`add-prompt-version`（提示词 + schema + promptfoo 用例）、`add-swiftui-screen`（Model + View + 快照）。模板里写清步骤、要改的文件和完成标准，比每次重新描述稳定得多。

这些模板落地为 `.claude/skills/<name>/SKILL.md`，与 hooks（拦截受保护文件、编辑后格式化、结束前快速验证）、两个只读审阅子代理、`.mcp.json`（GitHub 只读、Sentry staging、XcodeBuildMCP、Playwright MCP，版本固定）一起入库。完整清单与配置示例见 `05-toolchain-and-resources.md` §6 与附录 E、F。

## 21. Vibe coding 最佳实践（分端）

四个子系统对 AI 代理的友好程度差别很大：管理后台最适合放手让代理写，iOS 的系统能力部分最需要人工与真机把关。

| 子系统 | 代理擅长 | 必须人工把关 |
| --- | --- | --- |
| iOS | SwiftUI 页面、Model、单元测试、站点规则解析 | Keychain 属性、AVAudioSession / 后台模式、StoreKit、App Attest、证书固定、CarPlay；以及所有只能在真机上验证的行为 |
| 后端 | 路由、校验、仓储层、集成测试、队列任务 | 配额账本、签名与会话、加密与删除、迁移 SQL、提示词 |
| 管理后台 | CRUD 页面、表格筛选、图表 | 写操作的角色权限与审计 |
| 测试台架 | UI、runner 接线、报告生成 | 期望结果与门禁阈值的任何修改 |

### 21.1 iOS

- **不让代理碰 `.xcodeproj`**：只改 `project.yml` 与 SPM `Package.swift`，再跑 `make project` 重新生成。这消除了 pbxproj 被改坏的最大风险。
- **命令行可验证**：`make ios-test` 封装 `xcodebuild test`（指定模拟器），代理声称完成前必须跑通；也可以接入 XcodeBuildMCP（版本固定，见 05 §6.3），让代理在模拟器上构建、运行、截图，直接拿到编译错误与测试结果。
- **写清 API 基线**：在 `apps/ios/AGENTS.md` 中列出“最低 iOS 18、Swift 6”与替代关系：用 `@Observable` 而不是 `ObservableObject`；用 async/await 而不是回调；用 actor 而不是 `DispatchQueue` 加锁；用 StoreKit 2 而不是 StoreKit 1。代理的训练数据里旧写法很多，不写清楚就会反复出现。
- **并发错误要修根因**：禁止用 `@unchecked Sendable`、`nonisolated(unsafe)` 压掉编译器报错，用 SwiftLint 自定义规则拦截，确需使用时写明理由并人工审核。
- **让代理“看见”界面**：每个页面有注入假数据的 SwiftUI Preview 和快照测试；代理改 UI 后更新快照并把差异图放进 PR，交人工确认。视觉取值只能来自 `DesignSystem` token，禁止在页面里写死颜色和字号。
- **原型是参照不是代码**：把 `prototype/ios-app` 的冻结截图与 `DESIGN.md` 作为上下文提供，行为以 PRD 7.3 为准。
- **系统能力用参考实现**：Keychain、音频会话、后台任务、StoreKit 各写一份经过人工验证的小封装，放在 Infra 包里；代理之后只调用封装，不重新写底层代码。
- **真机清单**：CarPlay、蓝牙线控、锁屏、来电中断、App Attest、Share Extension 内存都不能靠模拟器验证，每次发版前按清单人工过一遍。

### 21.2 后端

- **契约先行的固定顺序**：改 zod schema → `pnpm contracts:gen` → 写路由测试 → 实现 → 更新 Swift 客户端调用。用 `add-endpoint` 模板固化。
- **集成测试用真库**：Testcontainers 起 PostgreSQL 与 Redis，不让代理 mock 数据库。代理写的 mock 往往和真实行为不一致，测试过了线上仍然出错。
- **幂等与重投必须有测试**：涉及 Stream、队列、配额的代码，要求代理同时提交“同一消息投递两次”“处理中途崩溃”的测试用例。
- **迁移只生成不手改**：用 `drizzle-kit generate`；已发布的迁移文件禁止修改（CI 校验哈希）；人工审 SQL，重点看锁表与“先扩后缩”。
- **日志红线自动化**：用 lint 规则或测试禁止 `console.log`、禁止把 `request.body` 或正文字段传给 logger。
- **提示词不过拟合**：代理修改提示词时必须跑全量 promptfoo 套件，不允许只为了让某一条用例通过而改。提示词新版本由人工批准进入配置包。

### 21.3 管理后台

- **用 Refine 脚手架提速**：新资源用 Refine 的资源生成能力产出列表 / 详情 / 编辑页骨架，代理再按 contracts 补字段。
- **权限矩阵写成表驱动测试**：每个写接口在一张“接口 × 角色 → 允许 / 拒绝”表里登记，测试遍历全表；未登记的接口测试直接失败。这样代理新增接口时不会忘记权限。
- **只用 Ant Design 组件**：不引入其他 UI 库或自定义 CSS 框架，保持代理产出风格一致。

### 21.4 测试台架

- **不允许代理通过改期望值让门禁变绿**：`evals/fixtures/**/expected*` 与门禁阈值配置放在必须人工审核的路径里。
- **线上问题回灌样本**：生产中发现的注入或译错案例，去标识后由代理整理成新的 fixture 与期望结果，人工确认后入库。
- **花费上限**：runner 对单次运行和每日总额设预算，超出即中止，防止代理反复跑真实厂商评测。

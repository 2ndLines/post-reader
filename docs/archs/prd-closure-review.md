## 0. 结论

主链路「登录 → 采集 → 生成 → 播放」在需求、设计、门禁三处是闭合的。断点集中在**链路的尾端**：出了问题之后谁发现、谁处理、用户看到什么、钱怎么算、数据去哪儿。

本次共检查 16 条业务链路，发现 25 个断点：

| 严重度 | 数量 | 含义 |
| --- | --- | --- |
| 高 | 9 | 链路实际断开：上线后会出现无法处理的客诉、无法止血的故障、无法证明的合规义务，或涉及用户的钱 |
| 中 | 11 | 链路能走通但依赖口头约定，或有要求没有验收依据 |
| 低 | 5 | 文档不一致或口径未定，不阻塞开发 |

三个最需要先拍板的问题：

1. **订阅事件如何改变权益与配额**（F06）：升级、降级、过期、退款、宽限期的规则主 PRD 没有写，后端、后台、台架都无法给出确定行为。
2. **紧急止血手段**（F08）：所有开关都在 Git 配置里，改一次要走完整门禁（单区最长 60 分钟），厂商故障或注入事件时无法快速止血。
3. **国内投诉举报与实名要求**（F16、F17）：主 PRD 未覆盖，需合规负责人确认后才能定后台与客户端的范围。

## 1. 评审方法

一条业务链路闭合，要求下面六环都有明确的归属文档和可验证的结果：

| 环 | 问题 | 通常归属 |
| --- | --- | --- |
| 触发 | 谁、在什么条件下发起 | 主 PRD |
| 处理 | 系统怎么做，失败怎么办 | 主 PRD + 架构 02 |
| 用户可见 | 用户看到什么、能做什么 | 主 PRD（iOS） |
| 运营可观测、可干预 | 内部人员能否发现并处理 | 管理后台 PRD |
| 质量可验证 | 上线前能否自动证明满足要求 | 测试台架 PRD + 主 PRD 第 12 节 |
| 数据归宿 | 产生的数据存多久、何时删除 | 主 PRD 第 9 节 + 架构 |

### 9.3 已确认无冲突的规则（抽查）

首段延迟目标（1.5 s / 2.8 s / 300 ms）、共享扩展内存（< 15 MB）、本地音频缓存（100 MB）、倍速五档与按 1.0× 计费、强制升级只放行 `GET /me`、耳机与 CarPlay 上一首 / 下一首对应帖内章节、后台采集只在音频后台播放期间进行、订阅事件表（主 PRD 11.4 与本评审 R4 内容相同）、两区数据导出与注销时限的默认值、可豁免门禁清单。

### 9.4 仍需负责人决定

1. **U14 区域不匹配的判定方式**：默认按 App Store 店面判定。若希望精确识别「该 Apple ID 已在另一区注册」，需要两区之间交换账户标识的摘要，属于跨境数据传输，需合规负责人评估。
2. 第 10 节与主 PRD 第 13 节其余待确认项，未决前按默认执行（00 D16）。

## 11. 长远方案修订（2026-11-26，负责人决策）

**原则**：杜绝临时方案与「以后再换」。技术链路、协议、数据模型、存储与部署形态按业务的长期形态一次选对；功能范围可以分期，但扩展点从第一版起预留。
